# Architecture vs Implementation Status

Comparison of the [architecture document](architecture-doc.md) against what is actually implemented in the codebase, as of 2026-10-11 (v0.1.15 + the `main` commits since).

**Two engines.** Everything below exists twice unless a line says otherwise: the original **Java engine** (`node-core` over `networking`/`consensus`/`myotis-evm`/`myotis-ens`, Besu EVM, Milagro or native-blst BLS) and the **Rust engine** (`rust/` — `myotis-core`, `myotis-consensus`, `myotis-net`, `myotis-evm`, `myotis-engine`; blst, revm), both behind the same engine contract (`:myotis-api`) and selected per network by `:myotis-engines` (`myotis.engine=auto|rust|java`, default `auto` = the Rust engine wherever it can serve). The Rust engine is the primary one: it is the default selection, the only engine on iOS and on Android below API 33, the engine the Node.js addon embeds, and ahead of the Java engine on features (the log index behind `eth_getLogs`, Tor routing, state overrides / EIP-7702 / contract creation in the EVM, the `finalized` tag on state reads, Amsterdam). "Rust only" / "Java only" below name the exceptions. Parity is pinned by shared conformance vectors (BLS fixtures, a captured mainnet light-client corpus, the EL verification-ladder vectors) and by golden JSON tests on both sides; the remaining behavioural differences are tracked in [TODO.md](TODO.md) (#342 parity entries).

## 1. Establishing a Trusted Chain Head — Sync Committees
**Implemented (both engines)**

- Beacon light client with bootstrap, finality updates, and sync-committee rotation — Java `BeaconLightClient`/`LightClientProcessor`, Rust `rust/myotis-net/src/sync.rs` over the sans-I/O verification core `rust/myotis-consensus`.
- Bootstrap pinned to a hardcoded beacon block root per network — the `@checkpoint:mainnet|sepolia|gnosis` marker regions of `NetworkConfig.java`, mirrored in `rust/myotis-net/src/sync.rs` (deliberately not duplicated here: a copy in prose goes stale on every refresh). `./gradlew refreshCheckpoint [-Pnetwork=…]` rewrites both engines from one multi-operator fetch; `java_and_rust_checkpoints_agree` fails if they diverge. Embedding hosts can supply a fresher root themselves (`createWithCheckpoint`, C ABI / Node addon, ABI ≥ 26; the Java engine refuses to resume such a directory).
- BLS12-381 with the ≥2/3 participation gate. Java: pure-Java Milagro AMCL or the native blst backend (`rust/myotis-bls` over JNI) behind the `BlsBackends` seam — `myotis.bls.backend=auto|milagro|native|compare`, default `auto` (native when the library loaded: the daemon and Android ship it, the desktop app bundles no blst library and runs Milagro). Rust: blst directly. Non-canonical encodings, non-subgroup points and identity points are rejected on both sides.
- Light-client req/resp over libp2p (TCP + Noise, yamux/mplex; jvm-libp2p on the JVM, rust-libp2p in Rust, which also speaks QUIC). Both engines register all four light-client protocols but request only three — `bootstrap`, `updates_by_range` and `finality_update` (the Java `requestOptimisticUpdate` has no callers; the Rust sync loop never asks for it) — so on both the optimistic head is the attested header of the finality updates they poll. Both engines run a **gossipsub** router with nothing subscribed or published (#425) — enough to stop Lighthouse from banning a peer that fails gossipsub negotiation, the 12-hour ban that stalled cold starts up to v0.1.8 (#422); subscribing to the light-client topics is still not built ([plan](../plan-gossipsub-subscription.md)).
- Every update is verified under the fork active at its signature slot, from the per-network fork schedule in `NetworkConfig` / `ChainConfig` (#430); a signature from the next period is checked against the next committee (#429). **Gloas** (Glamsterdam's CL half) is scheduled on Sepolia (epoch 353,024) and both light clients decode and verify the Gloas shapes — fork-keyed decoding, the shape gate before BLS, the execution anchor resolved by block hash (#501, [glamsterdam-plan.md](glamsterdam-plan.md)); mainnet and Gnosis have no Gloas date yet.
- `SYNCED` requires the held committee period to equal the wall clock's **and** the finalized slot to be within 5 epochs of it (`SYNCED_SLOT_SLACK_EPOCHS`, both engines), so a stalled or withheld feed drops the node to `CATCHING_UP` — the signal for a withholding relay ([readiness doc](readiness-and-verified-head-age.md)).
- **Weak-subjectivity gate** (both engines): an anchor older than the network's bound — 13 periods on mainnet and Sepolia, 3 on Gnosis — parks the client in `STALE_ANCHOR` instead of syncing; consent is per run (`accept-stale-anchor`, the apps' dialog, `-Dmyotis.beacon.acceptStaleAnchor`) or the bound is raised live (Settings, `-Dmyotis.beacon.wsBoundPeriods`). Re-checked at every bootstrap attempt and continuously while running.
- Persistence: the verified store snapshot (`sync-state[-net].snapshot`, "LCSS" v1/v2, byte-identical between engines, bound to the chain's genesis-validators-root) plus the state-root sidecar (Java only; the Rust engine neither reads nor writes it) and the CL peer cache, so a warm restart reaches `SYNCED` in ~10 s.
- Catch-up: one period per request from the first contact (Lighthouse's rate limit), pipelined across peers, hunting for batch-capable servers when throughput-bound (Rust, #424/#431); the Java client polls finality before walking peers on resume.
- CL peers are seeded from the persistent `CLPeerCache`, the pinned multiaddrs in `NetworkConfig` (census-pruned to servers that answered from two vantage points — 5 on mainnet, 2 on Sepolia (roost, and since 2026-10-09 zbox's Nimbus again — no public census-verified server has served Gloas-era data since the fork), 8 on Gnosis at the last census, with [roost](../rust/roost/README.md), the project's own light-client server, the first entry of each list) and **discv5** (Java: the ConsenSys library as the `com.github.biafra23:discovery` Android fork; Rust: the `discv5` crate), filtered by `eth2` fork digest; both engines run targeted lookups toward the pinned servers (#348, #351). EIP-1459 DNS remains wired on the Java side with an empty CL tree.
- Extraction of the execution payload header (state root, block hash, number, base fee) through the execution branch; SSZ types for every light-client container in both engines.

## 2. Verifying Historical Blocks — Trusted Accumulator Snapshots
**Partially implemented (unchanged)**

- Header-chain verification up to 8,192 blocks from the beacon-attested block (walk parent hashes) — both engines (`verify.rs`, `VerifiedAccountQuery`).
- Block verification against the beacon `ExecutionPayloadHeader.block_hash` works.
- The Rust log index walks parent hashes **without** a depth limit for its own purposes — the backfill descends from a beacon-anchored trust cursor to a contract's deployment block, and its head-gap bridge spans up to 500,000 blocks — but that anchors logs, not arbitrary block reads (§11).

**Not implemented:**
- `historical_summaries` / `historical_roots` lookup from beacon state (would remove the 8,192-block header-chain bound; note the JSON-RPC block reads are capped at 512 blocks below the head before that bound is ever reached).
- The pre-Merge epoch-hash accumulator — the README's trust-model section still lists it as a designed anchor; no code uses it.
- Pre-merge blocks return `failReason: "preMergeBlock"` with no verification path.

## 3. Transaction History — TrueBlocks via IPFS
**Implemented as a debug-only scan (Java engine, mainnet only)**

- Scan/parse service in `:tx-history` (`TxHistoryService`), shared by the daemon's `get-transactions` IPC stream and the desktop **and Android** Query tabs (streaming UI: block-number placeholders upgrade in place to parsed rows, progress + Stop). It wraps the Java engine's raw `RLPxConnector` (the documented exemption in `CLAUDE.md`), so it is unavailable on the Rust engine and on iOS.
- **Dynamic manifest CID discovery**: the latest mainnet manifest is read from the UnchainedIndex_V2 contract (`manifestHashMap(publisher, "mainnet")`, `0x0c316B70…183d`) via myotis' own verified `eth_call`; the publisher address comes from verified ENS (`publisher.unchainedindex.eth`, chifra's preferred publisher — the map is permissionless, so only that slot is trusted). Fallbacks when the node isn't synced: 24h-cached CID, then a hardcoded known-good manifest.
- Blooms + index chunks are fetched from an IPFS **HTTP gateway** (content-addressed, but the bytes are not re-hashed against their CIDs — only size- and parse-checked, `UnchainedIndexStore`; the doc's "IPFS bitswap" was never built) and disk-cached under `trueblocks/` (immutable, no TTL; truncated responses rejected against manifest sizes).
- Block bodies fetched from devp2p peers; txs decoded via `EthTxDecoder` (legacy, EIP-2930, EIP-1559, EIP-4844, EIP-7702; sender recovered from the signature) and classified (ETH transfer / ERC-20 transfer of well-known tokens / call / creation).

**Not implemented:**
- Transaction verification against `transactionsRoot` on this path (`verified` is hard-coded `false`). Per-tx verification exists on the JSON-RPC path (`eth_getTransactionByHash`, `eth_getTransactionReceipt`, §10); wiring it into the scan is still pending.
- Balance reconciliation for completeness checking.
- Non-mainnet indexes.
- **A fresh index.** Upstream publishing appears stalled: the designated publisher's newest mainnet manifest is indexed to ~block 23.0M (~a year behind head as of mid-2026), so recent history is absent. Both surfaces warn loudly (UI banner; `stale`/`indexAgeDays`/`warning` on the IPC `Started` line beyond 100,000 blocks of lag). Planned remedy: a self-published index (run the TrueBlocks scraper, pin the chunks, add the IPFS peer address to Myotis).

## 4. Fetching and Verifying Block Data — devp2p
**Implemented (both engines)**

- Full devp2p stack in both engines: discv4 discovery, RLPx ECIES handshake and AES-CTR framing, eth/66–69 (eth/69 `BlockRangeUpdate` and bloomless receipts included); the Rust engine also eth/70 (EIP-7975 partial receipts) and eth/71 (EIP-8159 block access lists), #691. The Rust stack is hand-rolled on small primitive crates (no reth); its RLP decoding of unsolicited peer frames is allocation-bounded (#454).
- `GetBlockHeaders`, `GetBlockBodies`, `GetReceipts`; bodies verified by rebuilding the transactions trie, receipts against `receiptsRoot` (eth/69's omitted `logsBloom` is recomputed first). Powers the block/receipt reads, `eth_feeHistory`'s reward percentiles and the log index.
- Block header verification against the beacon chain (a header chain walked down from an attested block hash; a matching state root alone never vouches for a header).
- **Rust engine**: block, receipt and `eth_call` state reads are **hedged** — a second peer is raced after 3 s near the head (6 s for bulk reads), and peers that keep losing are evicted (#457); the `eth_call` prefetch wave stops waiting on a peer that has answered none of our requests for 6 s (silence, not a request's age, so a slow link is not cut), reports it outpaced when the call's other peers were delivering meanwhile (so the silence was not our own link), and asks a peer that went silent or lost a race in the call only after the others; `eth_sendRawTransaction` answers at the first peer that takes the bytes, and the other writes get 5 s more, cut at once by a pause or stop (#320); the fee reads stay sequential, as hedging them would duplicate multi-MB downloads on every head; peers are admitted, ranked and struck by their announced head (`BlockRangeUpdate`, or a probe on eth/68), and readiness is gated on `snapServingPeers` — pooled peers that can answer at the anchored head *now* (#465); the by-number header window is anchored at the finalized block, honouring the `finalized` tag (ABI 30). The Java engine rotates `GetBlockBodies`/`GetReceipts` requests across peers instead of one-shot (#387) and evicts snap peers on repeated verified-read failures (#417), but has no hedging or serving count.
- EIP-1459 DNS-based bootnode discovery — both engines, with different reach. **Java** (`DnsEnrResolver`, `EnrTreeUrl`): on startup and on the snap-peer maintainer's refresh, over the system resolver or the host's DNS servers (Android), with public fallbacks. **Rust** (`el/dnsdisco.rs`, #539 part 3): on hosts that allow it (`myotis_set_dns_discovery`, ABI 39 — the JVM desktop and daemon and `myotis-rpcd`, which resolve through the system resolver; off on Android, whose DNS servers have no engine port yet, on iOS, and in the Node addon, which exposes no switch yet) and never while Tor is enabled; it verifies the root signature AND that every record hashes to its label AND each leaf's own signature (the Java walk checks the root only), judges each leaf's `eth` fork id before it becomes a dial candidate, dials the candidates in batches of 10 per 10 s while the pool is below target, re-walks every 4 min while it stays short, and nudges up to 32 of the tree's UDP endpoints into discv4 as DHT seeds. Mainnet and Sepolia trees pinned on both engines; Gnosis has none (the Java engine dials pinned enodes instead; the Rust engine relies on its bootnodes). The Rust engine otherwise seeds from the bootnodes, the cache, discv4, Sepolia's pinned enode and host-supplied seed pins (`myotis_set_boot_enodes`, ABI 31; `myotis-rpcd` via `--boot-enodes`). Since #539 its discv4 also asks every discovered node for its EIP-868 ENR and keeps a node whose `eth` fork id (EIP-2124) is another chain's from the pool before any TCP dial (`enrfilter.rs`); a node that answers with no `eth` entry, or not within 3 s, is dialed as before, a node whose record gives it no TCP port on the address family it is seen at (`tcp` for IPv4; `tcp6`, else `tcp`, for IPv6 — an address without any TCP port is the EF NodeOps bootnodes' shape) is never dialed there (it stays a source of neighbours), and the eth Status check stays the authority. Before that, a node's network was learned only after a full handshake — 3311 foreign nodes blacklisted in 18.8 h on Sepolia.
- **Fork watch** (#491): an EIP-2124 upgrade advisory on both engines — peers' fork ids are judged against the pinned schedule and a network that has forked past this build surfaces `upgradeAdvisory` on `status`. Enabled on Sepolia first. Its consensus-layer twin (`ClForkWatch` / `cl_fork_watch`) runs on every network: discv5 ENR `eth2` fields and peers' libp2p Status digests are judged against the build's `ForkSchedule`, so a fork is noticed without an EL peer; the two advisories merge into the one `status` carries ([glamsterdam-plan.md](glamsterdam-plan.md) A.2).
- **Data usage** ([data-usage.md](data-usage.md)): each network counts its bytes on the wire — RLPx, discv4, libp2p (and discv5 on the Rust engine) — and keeps today's total, with the part moved on a metered network as the host reports it (`setNetworkMetering`; Android and iOS push it from the OS), in `status` (`dataUsage`, `networkMetering`), JSON-RPC `myotis_status` and the Status screen. Tor's own traffic and DNS are not counted.
- Peer caching across sessions, byte-identical between engines: the EL cache (`peers[-net].cache` — snap quality flags `snapok`/`snapbad`; a peer is evicted after 50 consecutive connect failures on both engines, and the Rust engine persists a `snapbad` verdict only when another live peer witnessed the failure, where the Java engine records verdicts unconditionally) and the CL cache (`cl-peers[-net].cache`, evicts after 3 consecutive failures).
- Inbound: neither engine accepts inbound RLPx (outbound dialer only; [design](inbound-connections.md)). Both answer peers' `GetBlockHeaders` from a small served-header window (default 32, Settings-adjustable) so eth/69 peers keep them; the Rust libp2p host accepts inbound CL connections but serves no light-client protocols (roost does).

**Not implemented:**
- EIP-4444 fallback strategies; inbound EL connections; eth/70–71 on the Java engine (Amsterdam's partial receipts and BAL exchange — the Rust engine speaks both, #691; Glamsterdam plan, B.5).

## 5. State Data — SNAP Protocol
**Implemented (both engines)**

- snap/1 or snap/2 (EIP-8189; the highest version shared with the peer) negotiated alongside eth; `GetAccountRange` and `GetStorageRanges` with Merkle-Patricia proof verification (Java `MerklePatriciaVerifier`, Rust `myotis-core`'s hand-ported verifier), `GetByteCodes` verified by `keccak256(code) == codeHash`. Both engines route every state read through the **range** messages, never `GetTrieNodes` — only the range responses carry the root-to-leaf proof (the Java `SnapPeer.getTrieNodes` API name is a misnomer: `EthHandlerSnapPeer` translates each path set into `GetAccountRange`/`GetStorageRanges`). `GetTrieNodes` is wired at the wire layer only (Java, snap/1 connections; snap/2 removed the message).
- ERC-20 balance lookup via `keccak256(abi.encode(holder, slot))` mapping; full beacon cross-verification (proof → state root → beacon root).
- The snap query root comes from the beacon anchor, not a peer's stale handshake head (#356); `latest` reads retry briefly while peers trail the anchored head (#416).
- **`finalized`** on the state reads: the Rust engine proves against the finalized state root with no fallback and labels the result `anchor: "finalized"` (ABI 32); the Java engine would resolve `finalized` to its head, so the router refuses the tag there (`-32602`, `VerifiedReads.supportsFinalizedTag`, #366). A state read pinned to `safe`, `earliest`, an out-of-spec selector or a number — or the hash of a block — more than 64 blocks behind the head is refused by the router with the permanent `-32602` before any engine runs (#366); a block hash is resolved by the engine header-only (ABI 47: the attested head at once, any other hash in one 64-block header window anchored at the head) and served as that block's number, and one this node cannot place (not reached yet, older than the window, or on a fork) is declined with the retryable `-32000` (#641); only the one-block race between the router's head and the engine's still flattens an engine-side refusal to `-32000` ([TODO.md](TODO.md)).
- Caches: the Java `StateProofCache` keys accounts by state root and **storage slots by the account's storage root**, so unchanged contracts replay across head advances; the Rust twin still keys storage by world state root (a parity gap recorded in `06-rust-phase-notes.md`). Both engines run the **read-stats shadow cache** (`read-stats` IPC, the Status tab's "Reads"/"Cacheable" rows) that measures what a further cache would save without serving anything ([read-stats.md](read-stats.md)).

**Not implemented:**
- NFT ownership queries (same mechanism, not exposed).
- Vyper storage slot layout support.

## 6. ENS Resolution — Via Local EVM over SNAP-Verified State
**Implemented (both engines; full record-type coverage)**

Resolution runs the ENS contracts in the local EVM (§9) with state served from SNAP proofs — ENSIP-10 wildcard resolution and CCIP-Read (ERC-3668) work for every record type. The Java resolver walks the Registry directly (ENSIP-10), the Rust engine likewise over its own verified `eth_call`s.

| Record | Spec | IPC command |
|---|---|---|
| Forward address | ENSIP-1 | `resolve-ens` |
| Reverse (address → name, with the mandatory ENSIP-3 forward check) | ENSIP-3 | `reverse-ens` |
| Multi-coin address | ENSIP-9 / SLIP-44 | `resolve-ens-addr-coin` |
| Text records | ENSIP-5 | `resolve-ens-text` |
| Content hash | ENSIP-7 | `resolve-ens-contenthash` |
| Ownership — registrant, manager, resolver, expiry and grace period, through the NameWrapper | ENS registry + `.eth` BaseRegistrar | `resolve-ens-ownership` |
| Public key | EIP-619 | `resolve-ens-pubkey` |
| ABI metadata | EIP-205 | `resolve-ens-abi` |
| DNS records | ENSIP-8 | `resolve-ens-dns` |
| Interface implementer | EIP-1820 over ENS | `resolve-ens-interface` |

Every query takes a **resolution root**: Java `AUTO` (finalized first, peer head as fallback) / `FINALIZED` / `PEER_HEAD`; Rust `auto` / `finalized` / `optimistic` — the Rust engine has no peer-claimed mode, every answer is beacon-anchored. All hosts use `AUTO` (Android's `NodeService.setEnsResolutionRoot(...)` exists for an embedding host; no UI exposes the choice).

CCIP-Read end-to-end: `OffchainLookup` reverts caught by `CcipReadEvmExecutor` (Java) or returned to the host as the gateway tuple and re-entered via `ccipCallback` (Rust, driven by `CcipDriver` on the JVM hosts); the HTTP transport is the injectable `HttpGateway` port — `java.net.http` on the daemon and desktop (`JavaHttpCcipGateway`), `HttpURLConnection` on Android (`UrlConnectionHttpGateway`); both cap the response at 1 MiB and the whole request at 15 s (on Android from the connect on: a stalled DNS lookup before it is bounded by the platform resolver). Validated against the EIP-3668 demo gateway and Coinbase IDs (`*.cb.id`). On both engines a reverse lookup's claim and its forward check get a CCIP round each, so an off-chain primary name verified off chain takes two (on the Rust engine the offchain envelope names the claim a round forward-verifies, `reverseClaim`, and `CcipDriver` echoes it into the callback). **iOS has no CCIP-Read yet** — off-chain names report "resolves off-chain (CCIP-Read), which this app doesn't support yet".

**ENSv2 (#671), in progress.** Sepolia runs on ENSv2: its v1 contracts "still exist but are no longer in use". Forward reads of a v2 name reach it through the `ENSV2Resolver` the v1 registry sets on `eth`, and an address without a reverse resolver of its own is asked of the `reverse` node's wildcard resolver, which answers v2 primary names (on mainnet too, for a name it keeps). Ownership is refused for a name ENSv2 decides — where ENS's Universal Resolver (`0xeEeE…EeEe`) names a root registry and does not hand the name to its v1 mirror — because v1's registry and registrar would read it as unowned. Mainnet is unaffected until ENSv2 activates there. Still to come: resolver discovery through the Universal Resolver, and ownership read from ENSv2 (Rust engine).

Network coverage: mainnet and Sepolia (`NetworkConfig.hasEns`); on Gnosis, Genome's `.gno` names through the same resolver (forward records and ownership; reverse lookups are refused). (`EnsResolver.forChainId` still carries holesky's addresses, dead code since the network was retired.)

Reverse resolution also names the log index's imported entries (verified reverse-ENS, Rust engine), so a generated index file cannot lie about who a contract is.

**Not implemented:**
- ENS over JSON-RPC (there are no `ens_*`/`myotis_ens*` methods; wallets resolve through `eth_call` themselves) and a UI surface for reverse lookup or the resolution root.
- L2 / cross-chain name handling (ENSIP-19 L2 primary names) beyond what an ENSIP-10 resolver serves through CCIP-Read.

## 7. Submitting Signed Transactions — devp2p Transaction Gossip
**Implemented (both engines)**

- `eth_sendRawTransaction` broadcasts the user-signed raw bytes to connected peers via the `Transactions` message (the Rust engine to every snap peer, re-pushing a not-yet-seen transaction on the wallet's receipt / `eth_getTransactionByHash` polls at most every 20 s until gossip echoes its hash — the Java engine runs the same 20 s gate on a timer), returns `keccak256(rawTx)`, and caches the bytes so `eth_getTransactionByHash` reports the tx as *pending* before it's mined. Myotis never signs — it only relays.
  - **Both engines, before anything else (#360, ABI 44):** the bytes must be a transaction this node relays — a legacy or type 0x1 / 0x2 / 0x4 transaction, strictly decoded (its type's exact fields, canonical RLP with nothing trailing, integers without leading zeros and no wider than the decoders read them, `to` empty or an address and never empty on type 0x4, access-list entries `[20-byte address, [32-byte keys]]` and type-0x4 authorizations `[chainId, address, nonce, yParity, r, s]` as geth decodes them — an entry geth cannot read fails the whole `Transactions` packet and gets the sending peer dropped), with signature values a peer accepts (v 27/28 or EIP-155, yParity 0/1, 0 < r < n, 0 < s ≤ n/2) and a sender the signature recovers. Anything else is refused with `-32602` and never broadcast: a junk byte used to be gossiped to every peer and answered with its keccak, a hash of nothing a wallet could find mined. A blob transaction (type 0x3), in either form, is refused too — the eth protocol forbids pushing one in a `Transactions` message, and geth drops the peer that does. The strict decode is also what makes the returned `keccak256(rawTx)` the decoded transaction's own hash. One gate per engine, same rules and same words: `EthTxDecoder.checkSendable` (Java) and `tx::decode_sendable` (Rust), their tests checking the same cases.
  - **Both engines, then (#665):** a transaction signed for another chain is refused with `-32602` and never broadcast, in geth's words: `invalid sender: invalid chain id for signer: have X want Y` (`tx::check_chain` / `EthTxDecoder.chainRefusal`, the same rule and words, on the typed `chainId` field or a legacy EIP-155 `v`). It used to skip the pre-broadcast check below and go out, answered with a hash no peer here would ever include. It rests on the signed bytes alone, so unlike that check it never fails open. A pre-EIP-155 legacy transaction names no chain and is sent as before. The Java engine runs it with the #360 gate in `GatedVerifiedReads`, before its wake wait, against the static network config, so a starting or paused node refuses at once. The Rust engine runs it in its own send entry point, against the handle's chain in any handle state (created, paused, running with or without an EL reader), so the Node addon, which has no readiness hold, refuses at once. The JVM `RustChainHandle` and myotis-rpcd hold a send first: the handle-less `check_raw_transaction_json` (ABI 45) they call before that hold knows no chain. At the hold's deadline both hand the send to a running handle, which refuses it, so a starting node answers with the permanent `-32602` after up to 90 s (`WAKE_WAIT_CAP_MS`, `--ready-wait`); the retryable error appears only where the engine is never asked (a JVM stack still paused at the deadline, a later element of an rpcd batch that already spent its wait). The iOS backend has no hold. Removing that latency needs the chain in the handle-less call, an ABI change.
  - **Both engines, before the broadcast (#531; Rust since ABI 36, Java since #360's follow-up):** the transaction is decoded and its sender's balance and nonce are read with proofs at a fresh head — the Rust engine's optimistic head, the Java engine's anchored head (the snap-servable block hash-linked up to it, which the warmer rebuilds every dozen seconds or so and every other state read is served from). Two Java differences follow from that head. It judges FUNDS only when the anchored head is the attested optimistic head itself: one block below it, a sender funded in the newest block, whose receipt this node already serves, would be refused. A used nonce it judges at any fresh anchored head, since a nonce only grows. And under the same freshness bound it judges less often than the Rust engine: on mainnet's 12 s slots often, on Gnosis's 5 s slots (a 16 s bound against the warmer's cadence) rarely; it never judges by older state. Making it judge more often is a head-cadence question (snap load), not the check's. The check waits for the read at most 2 s; the read itself runs on rather than being cut mid-request — the Rust engine's for up to 20 s, the Java engine's until its oracle gives up (at most 8 attempts of 10 s each, so a read can hold its slot for up to 80 s) — and at most four run at once (past that a send goes unchecked). One rule set, twice: `send_check.rs` / `ElReader::pre_broadcast_check` and `SendCheck` / `VerifiedRpcBackend.preBroadcastCheck`, their tests checking the same cases in the same words.
    - **Refused, never broadcast,** when the sender cannot pay `value + gas × fee` (gas price, or max fee per gas) or the nonce is below the account's. The answer is geth's `-32000` with geth's txpool words: `insufficient funds for gas * price + value: balance B, tx cost C, overshot D`, or `nonce too low: next nonce N, tx nonce M`. ethers v6 and viem classify these by their text.
    - **Judged only on fresh, verified state:** the account must be proven against the head's own beacon-anchored state root (the Rust engine's: BLS-attested; the Java engine's: hash-linked up to the attested head, and only once that link holds), and the head must be at most two block times plus 6 s old — by its own proven timestamp, and by when this node learned it advancing past an earlier head, on its monotonic clock, so a wrong wall clock cannot pass a stalled or restored head as fresh (the first head after a start, a restored snapshot's, is never judged by). Both bounds are checked again when the read returns, at the verdict. A light client learns block N from block N+1's sync aggregate, so its head is normally one to two blocks old.
    - **Fails open:** a stale or (Java) not yet anchored head, an unreadable wall clock, Tor-routed reads (Rust; they answer at a session's own head), four reads already in flight, or an account read that times out, fails, is unverified or is not proven against the head's root is broadcast as before; the log says why and how old the head was. The Java engine never builds or waits for a head to judge by: it judges at the head the warmer last installed, or not at all.
    - **Not errors:** a nonce gap (wallets send several in a row). Each transaction is judged alone against the balance: geth's pool also counts the sender's transactions it already queued, which this node does not see.
    - **Logs:** every send logs its tx hash (broadcast, refused, or not broadcast for want of a peer), the first gossip sighting of one logs its latency, and a watch that expires never echoed back, with no receipt served for it, logs "likely dropped".
    - **Hosts:** they serve the refusal through `VerifiedReads.sendRawTransactionDetailed` (`SendResult`: `REJECTED` here, `REFUSED` for the #360 gate and the #665 chain check above). Every host runs the #360 gate before its readiness hold, so a starting or paused node answers bytes that are no transaction with `-32602` at once: the Java engine's `GatedVerifiedReads` before its wake wait, the JVM `RustChainHandle`, the iOS backend and myotis-rpcd through the engine's handle-less `check_raw_transaction_json` (ABI 45) before their wake wait, handle lookup and `--ready-wait` hold, and the engine's own entry point before its handle lookup (the Node addon has no readiness hold).
- Propagation is confirmed by watching our own hash return over `Transactions` / `NewPooledTransactionHashes` gossip (decoded only while a send is unconfirmed); the pending-nonce overlay lets back-to-back sends from one account not collide (the one deliberately unproven value — it only raises the verified mined count, only for our own broadcasts, TTL-bounded).
- Confirmation tracking: `eth_getTransactionByHash` / `eth_getTransactionReceipt` scan the recent beacon-verified block window (initial lookback 8 blocks, then forward); once the tx appears (verified vs `transactionsRoot`) the wallet sees `blockNumber` populate and the receipt is verified against `receiptsRoot`.
- Validated end-to-end on a real device: MetaMask builds and signs, Myotis broadcasts over devp2p, the receipt confirms on-chain — no proxy.

**Not implemented:**
- `GetPooledTransactions` / mempool serving (announce-then-fetch) — outbound broadcast uses the direct `Transactions` message only.
- EIP-4844 blob-sidecar gossip (out of scope; L2-sequencer territory).

## 8. Gas Estimation
**Implemented (both engines) — `eth_estimateGas` over JSON-RPC**

Geth's search for the lowest gas limit at which the transaction succeeds, plus a 15% buffer, at least the EIP-7623 calldata floor (Prague+), capped at the caller's `gas` (without one, the block's gas limit) and at the fork's transaction gas cap (EIP-7825's 2^24 from Osaka). A plain value transfer to a code-less, non-precompile account short-circuits to exactly 21000 with no EVM run (pre-Amsterdam — EIP-2780 reprices transfers there). Revert and out-of-gas halts are errors, never a number: a revert reaches the wallet as JSON-RPC error `3` with the revert payload (engine ABI 23 added the estimate's revert payload); an estimate that does not fit the caller's `gas` or funds answers geth's `-32000` messages verbatim (`gas required exceeds allowance (N)`, `insufficient funds for transfer`), and a fee cap below the block's base fee — or, without a fee, a value the sender cannot cover — geth's "failed with N gas: …".

**The search (#509 stage 2, both engines).** A first probe at what the run at the ceiling drew plus the call stipend, with the 63/64 a nested call withholds, is usually the answer, and bisection stops within 1.5% of the lowest limit that works; the 15% buffer goes on top. One run's draw plus 15% was not a limit that works for a deep call chain or a contract that checks `gasleft()`. Unlike geth the search never goes below that draw (geth starts from the post-refund charge): a lower limit only "works" by running a different transaction, such as one whose inner call fails and is caught. Without a caller `gas` the ceiling is also bounded by the block's gas limit, where geth's search starts. A real mainnet RelayAdapt7702 shield — #509's transaction, recorded from the engine's verified reads with throwaway keys (`rust/testdata/evm/relayadapt7702-shield.json`) — replays in both engines and pins the answer. In the Rust engine the run at the ceiling goes through the speculative prefetch loop `eth_call` uses (#532). It used to be a single real run that fetched each piece of state it touched in its own round-trip; #532 measured 4–33 s. The search's probes then run on what the loop fetched. An `eth_call` of the same transaction at the same state root, as a wallet runs just before, leaves nothing to fetch through the caches they share. Each estimate logs an `EVM call breakdown` line at info, and each `eth_call` of a transaction object at debug. The line gives EVM runs, the reads waited on one at a time and in prefetch waves with the time each took, and the rest of the run, mostly the EVM's own time.

**The whole transaction object (#509, ABI 34).** Every field is applied or the request is refused with the permanent `-32602`, never dropped. The Rust engine (`myotis_evm::tx::TxRequest`, `EvmExecutor::estimate_tx`) applies EIP-7702 `authorizationList` (revm installs the delegations exactly as a mined transaction does, skipping an invalid tuple), `accessList`, the `gas` cap (below 21000 it is no cap, as in geth), the fee fields (`GASPRICE` reads the effective price; a non-zero fee cap bounds the ceiling by `(balance − value) / feeCap`), `nonce`, `type`, `chainId`, the block selector (including `finalized`), a state override, and contract creation (init code bounded by EIP-3860). The Java engine applies `gas`, the fee fields and the block; it refuses the two lists, state overrides, contract creation and `finalized` (it would answer from the head). Contradictory objects (a type-4 request without a list, a tip above the fee cap, `data` and `input` that differ, blob fields, another chain's `chainId`) are refused on both.

Acceptance corpus (`MainnetGasEstimationIT`, env-gated): ETH→EOA, ETH→contract (WETH deposit), ERC-20 transfer (USDC), ERC-721 transfer (ENS BaseRegistrar), Uniswap V3 exact-input swap, each cross-checked against a reference `eth_estimateGas` within 5%. `AnvilForkedBroadcastIT` broadcasts a transaction with the locally-estimated gas to an Anvil mainnet fork and asserts `gasUsed <= localEstimate` — the 15% buffer is sufficient on the wire. Verified on-device against MetaMask's send flow (`0x5208` in ~0.16 s for a plain send).

Fee suggestions are served verified — `eth_gasPrice`, `eth_maxPriorityFeePerGas`, `eth_feeHistory` — base fee from verified headers, priority-fee tips from bodies verified against `transactionsRoot`, reward percentiles from a gas-used-weighted walk over receipts verified against `receiptsRoot`. The Rust engine memoizes the fee reads per anchored head and refreshes them in the background (#510), so the confirm screen's fee poll is instant. Since #532 the memo also keeps each recent block's verified tips and gas weights, so a new head costs one body and one receipts fetch for all the fee reads a wallet polls. While a slow refresh retries, a value up to 5 blocks or 75 s old is served; a stale `eth_gasPrice` has its base-fee part raised by 12.5% for each block it is behind (EIP-1559's cap). A read that finds nothing usable waits at most 5 s (30 s for an `eth_feeHistory` pinned to a block number), then answers the retryable `-32000` and leaves the compute running for the next poll. It waits for a compute already running for the same read instead of starting another, and at most 4 such background computes run at once across all fee reads. For `eth_feeHistory` the host first falls back to its last good answer for the same request, up to about 13 minutes old; `eth_gasPrice` has no such fallback. A `[fee-reads]` log line counts fresh, stale and missed reads and the refresh outcomes: every 5 minutes while fee reads flow, and when the follower goes quiet or the node pauses or stops.

## 9. Local EVM Execution
**Implemented (both engines) — `eth_call` and `eth_estimateGas`, ENS**

- **Rust engine**: `rust/myotis-evm` — **revm 43** (pinned exactly) behind a `SnapStateOracle` trait, sans-I/O; the network side (`rust/myotis-net/src/el/evm.rs`) serves it from the snap pool with hedged, batched proof fetches (chunks of 64, bounded in-flight requests). Per-chain fork tables for mainnet, Sepolia and Gnosis (London and later); **Amsterdam** (Glamsterdam's EL half) is served on Sepolia from its scheduled time.
- **Java engine**: `myotis-evm` embeds Hyperledger Besu's standalone EVM (`org.hyperledger.besu:besu-evm` 26.4.0; the `com.github.biafra23.besu` fork on Android). `DefaultEvmExecutor` runs one Besu pass over the snap-backed `StateOracle`; `PrefetchingEvmExecutor` wraps it; `CcipReadEvmExecutor` handles ERC-3668. Same three chains, London and later; Besu 26.4 stops at Osaka, so a Sepolia block from Amsterdam on is **refused** with a permanent `-32602` ("the Rust engine serves it") rather than mis-priced.
- Both engines run a **multi-hop speculative prefetch loop**: sentinel passes record accesses without blocking, then parallel batch fetches run, and the last two iterations are always real; the cap fails closed. So the round-trip-per-SLOAD latency does not dominate. Bytecode verified via `keccak256(code) == codeHash`; block context (`number`, `timestamp`, `coinbase`, `prevRandao`, `baseFeePerGas`, `gasLimit`, `chainId`, and Amsterdam's slot number) from the verified header only. EIP-7702 delegation designators are followed one hop, with the delegate warm from the start, as geth and revm start it.
  - **Java engine:** four iterations, and its `eth_estimateGas` still makes its run at the ceiling without the loop (`PrefetchingEvmExecutor.estimateGas` delegates to the serial executor).
  - **Rust engine, since #532:** up to twelve iterations, so ten discovery passes. The network oracle starts no discovery pass more than 15 s into a loop (`SnapStateOracle::keep_discovering`, as the EVM crate holds no clock); a pass under way still finishes its wave, and the real runs fetch what is left. Each wave also fetches the code of every contract its pass called or inspected with `EXTCODESIZE`/`EXTCODECOPY`, so a newly reached contract runs in the next pass, and leaves out what the caches already hold. A pass that needed no placeholder is taken as the real run. `eth_estimateGas`'s run at the ceiling goes through the loop too. Both it and an `eth_call` of a transaction object start with one wave for the sender, the target and each EIP-7702 authorization's delegate, then one for the code of the target and the delegates.
  - **Shield measurement:** on the recorded mainnet RelayAdapt7702 shield, the estimate went from 57 reads made one round-trip at a time to none, and a wallet's `eth_call` of it from 50 to none, each in 15 parallel waves. Its discovery takes eight of the ten passes.
- **`eth_call` fields** — the whole transaction object, applied as geth applies it or refused (#509 stage 2; `EvmExecutor::call_tx`, the Java `EvmExecutor.callTx`, engine ABI 35):
  - **Block selector.** Read by the router's one selector parser (#366): `latest`/`pending` = the head; `finalized` = the beacon-finalized block on the Rust engine, refused (`-32602`) on the Java engine, which would answer it from the head; `safe`, `earliest`, block 0, an empty string, bare digits and JSON numbers are refused (`-32602`); a number within 64 below / 16 above the head runs against head state, as does EIP-1898's `{"blockNumber":…}`; a block hash (bare or `{"blockHash":…}`) is resolved by the engine header-only to the canonical block it names (ABI 47) and judged as that block's number (#641) — a hash this node cannot place (not reached yet, older than its 64-block header window, or on a fork) is the retryable `-32000`; a number further behind is refused (`-32602`) by the router before the engine runs, on both engines — unless it is at or above a head the node itself reported in the last 15 minutes (then the retryable `-32000`); one ahead of the window is the retryable `-32000`.
  - **Gas and fees.** `gas` is the call's limit — capped at the engine's 30 M budget, as geth caps it at its RPC gas cap — so a limit below the intrinsic cost or the EIP-7623 floor is refused ("intrinsic gas too low: have N, want M" / "insufficient gas for floor data gas cost: …") and running out of it answers "out of gas"; a `gas` above the budget is capped to it, and a call that runs out there is refused (`-32602`: the answer would be for a smaller limit than the caller set). A non-zero fee must reach the base fee ("max fee per gas less than block base fee: …") and is debited from the sender before the call runs, with `GASPRICE` reading the effective price; fee or not, the sender must hold `gas × fee cap + value` ("insufficient funds for gas * price + value: …", geth's `buyGas`). A check failed before the run is worded as geth's `eth_call` words it, "err: <reason> (supplied gas N)" — each of these is `-32000` with geth's message, never return data.
  - **Rust engine only:** a **state override** (`code`, `balance`, `nonce`, `state`, `stateDiff`), **contract creation** (an absent or `null` `to` runs the init code; an empty-string `to` is a malformed address and is refused, not creation), `accessList` (charged and pre-warmed) and `authorizationList`; the Java engine refuses all four (`-32602`). Refused on both: blob fields, block overrides, contradictory `data`/`input`.
  - **Known differences from geth:** a fee-less call reads the block's real `BASEFEE` (geth zeroes it), and a plain call (no `gas`, fee or list) is not held to the sender's balance. Between the engines, the Java engine's plain call charges no intrinsic gas (calldata of any size runs with the full 30 M), where the Rust engine answers a plain call whose calldata alone outweighs the budget with geth's intrinsic/floor refusal.
- A reverting call answers error `3` with the revert payload and decoded `Error(string)` reason — MetaMask's ERC-165 probes depend on it.
- **`BLOCKHASH` (Rust engine, #664)** is served from verified data only (`rust/myotis-evm/src/database.rs`; [verification.md §9](verification.md#9-contract-calls-and-gas-estimation)): block N-1 is the call header's `parentHash`; from Prague on, an older block in the 256-block window is read from the EIP-2935 history contract's storage, proven against the call's state root and fetched in the prefetch waves like any slot; what the contract does not hold is proven by a header walk down from N's parent (`PoolOracle::fetch_block_hash`); the current block and anything older than 256 blocks are zero. A hash nothing proves fails the call (retryable), never zero. **Java engine:** still refuses — a call that executes `BLOCKHASH` fails (Besu's block-hash lookup throws), and never answers zero.
- **`eth_createAccessList` (Rust engine only, engine ABI 40; `EvmExecutor::create_access_list`).** The EIP-2930 access list the transaction touches, built as geth's `internal/ethapi.AccessList` builds it: the run is traced by a twin of geth's `AccessListTracer` (an inspector that lists the account and key of every `SLOAD`/`SSTORE`, and the address of every `BALANCE`/`EXTCODE*`/`SELFDESTRUCT` and every call), leaving out the sender, the recipient (for a creation, the address the contract gets) and the fork's precompiles, which every transaction warms anyway — except that a storage key always lists its account, so the recipient's own slots are in. The run is then made again with that list applied until the list stops changing (at most ten runs; a list that keeps changing is the retryable `-32000`), each run through the same prefetch loop as `eth_call`. The list is sorted by address and key, so the same run always gives the same list (geth iterates a map). The result is geth's `{accessList, gasUsed}`; a run that itself reverts or halts keeps its list and reports the failure in `error` next to it, never as a code-3 error. The request is `eth_call`'s, with the same checks (`EvmExecutor::prepare_tx_call`): the same gas limit, the same fee and funds checks (`-32000` in geth's words), a `gas` above the budget whose run runs out there refused, a state override applied — as reth's signature has it; geth takes no override — and contract creation served. The Java engine builds no access lists and refuses the method (`-32602`), before it is woken. Two deliberate differences from geth: a request without fee fields runs fee-less, as `eth_call` runs it, where geth fills in a fee from its own tip oracle and then holds the sender to `gas × fee` (an account below that fails geth's `eth_createAccessList` outright); and geth loops without a bound but its request deadline.
- Exposed over JSON-RPC as `eth_call`, `eth_estimateGas` (§8) and `eth_createAccessList`, and driving ENS (§6). `:myotis-evm:test` and the Rust crate's tests cover the executor stacks with deterministic fixtures; the EL verification-ladder vectors are shared.

**Not implemented / rough edges:**
- `BLOCKHASH` on the Java engine (refused, see above); `BLOBBASEFEE` reads revm's floor because no excess-blob-gas is passed; an EIP-1898 block object on the state reads is read as `latest` (`eth_call` and `eth_estimateGas` apply `{"blockNumber":…}` and refuse a hash).
- A dedicated "simulate" surface that decodes revert reasons for a UI — `eth_call`/`eth_estimateGas` cover the mechanism.
- Java engine: a cold head-context build (header-chain anchor + first snap fetch on a fresh peer) can take ~15 s; warm calls ~1 s.

## 10. Wallet Integration — Verified JSON-RPC on every host
**Implemented (MetaMask end-to-end; Bee and RAILGUN clients as PoCs)**

The `jsonrpc-server` module (Kotlin Multiplatform/Ktor) exposes the verification pipeline as a standard Ethereum JSON-RPC endpoint. `RpcRouter` maps the API onto the module's `RpcBackend` seam — `VerifiedReadsBackend` over the engine contract's `VerifiedReads` on the JVM hosts, `IosRpcBackend` on iOS — so **every host serves it**: the Android app, the iOS app, the desktop app and the desktop daemon (which additionally exposes the verified operations over its CLI/IPC socket). Loopback only (`127.0.0.1`; mainnet 8545, Gnosis 8546, Sepolia 8547 by default, user-settable in the apps), unauthenticated, no TLS, no rate limiting — a same-device wallet's endpoint, deliberately unreachable from other devices. **Strict permissionless mode** is the default and the only production mode: an unservable request returns `-32601` (not served verified) or `-32000` (can't answer right now), never proxied data. (A dev-only upstream proxy exists solely to discover what a wallet calls.)

Verified methods (`VERIFIED_METHODS` in `RpcRouter.kt`; per-method verification basis and the full error-code contract in the README's *Wallet API*): `eth_chainId`, `net_version`, `eth_blockNumber`, `eth_syncing`, `eth_getBalance`, `eth_getTransactionCount`, `eth_getCode`, `eth_getStorageAt`, `eth_getProof` (Rust engine; only at one of the last 128 heads the node held, the current one included, or the finalized block — exactly), `eth_call`, `eth_estimateGas`, `eth_createAccessList` (Rust engine), `eth_gasPrice`, `eth_maxPriorityFeePerGas`, `eth_feeHistory`, `eth_getBlockByNumber`, `eth_getBlockByHash`, the block-derived reads (`eth_getBlockTransactionCountBy*`, `eth_getTransactionByBlock*AndIndex`, `eth_getUncleCountBy*`, `eth_getUncleBy*AndIndex`), `eth_getTransactionReceipt`, `eth_getBlockReceipts`, `eth_getTransactionByHash`, `eth_getLogs` (log index, Rust engine), `eth_sendRawTransaction`, `eth_accounts`, `net_listening`, `net_peerCount`, `web3_clientVersion`, `web3_sha3`. Plus the node-introspection `myotis_status`, `myotis_beaconStatus`, `myotis_rpcCoverage`, `myotis_pause` / `myotis_wakeup` (the out-of-process wallet's background/foreground hooks). JSON-RPC 2.0 batches are handled element by element. Wallet quirks handled: reads pinned to a near-head block number are served from the head's state (a stale pin is refused, not answered with newer state); verified reads are held only while the node is actually waking up, at most 90 s (#432); a slow-call watchdog; the HTTP layer heartbeats whitespace so a long `eth_call` survives the wallet's read timeout.

**Hosts.**
- **Android** (`android-app`, minSdk 29) runs the whole stack as a foreground `NodeService` with a Compose UI (Status / Query / Settings, plus Logs / Index in Expert mode), every enabled network in one process, idle sleep with a daily catch-up pass, and warm-restart persistence. Below Android 13 (API 33) the Rust engine is the only engine — Besu's `UInt256` and Guava's futures need hidden `VarHandle` APIs — and Settings says so instead of offering the toggle (#433). The APK's dex is gated against the minSdk-29 API budget by `scripts/check_apk_min_api.py`, and CI boots the app on a minSdk-29 emulator.
- **iOS** (`app-ios` + `ios-app/`): the shared UI in a Kotlin/Native framework (`MyotisKit`) over the Rust engine's C ABI — the JVM engine never runs there. A development host more than an integration point: iOS suspends backgrounded apps (the node keeps running ~30 s after backgrounding), so a wallet embeds the engine instead; releases ship `MyotisKit.xcframework` and the raw-engine `MyotisEngine.xcframework` for Swift hosts. Its RPC backend does not wire `eth_getLogs` yet (`IosRpcBackend` has no `getLogs`, so the method answers `-32000` although the engine underneath holds the index).
- **Desktop app** (`app-desktop`): the same UI, jpackage `.dmg`/`.deb` bundling the Rust engine, opted out of macOS App Nap (it serves RPC to other processes), rolling logs under `~/.myotis/logs` with `myotis.log.level` / `myotis.log.rpc.level`. Two PoC build flavours (`-PbeePoc`, `-PrailgunPoc`) pre-seed a log index for a Swarm Bee node on Gnosis and for the RAILGUN wallet on mainnet and Sepolia — demo/debug artefacts, not production paths (§11).
- **Desktop daemon/CLI** (`app`): IPC over a Unix socket per network (`/tmp/ethp2p[-net].sock`), hosting one or several networks per process (`-Pnetwork=mainnet,gnosis`), each with its own EL/discv5/RPC ports; the command reference is in the README.
- **Node.js addon** (`rust/myotis-node`, napi-rs, ABI 46): the engine in-process for Electron/Node hosts (the Freedom browser's experimental Myotis tier), prebuilt for five platforms per release; wraps lifecycle, status, `requestAccountJson`, `ethCallJson`/`ethCallTxJson`/`ethCallOverridesJson`, `estimateGasJson`/`estimateGasTxJson`, ENS, `feeEstimateJson`, `sendRawTransactionJson`, and (#503) the block, receipt and transaction reads, `feeHistoryJson`, `getCodeJson`/`getStorageAtJson`, `getProofJson`, `getLogsJson` with the log index's config, status and snapshot import, and the `pending` nonce overlay — every read a dApp provider needs (`eth_blockNumber` is `statusJson().optimisticBlockNumber`), with the argument checks the JSON-RPC routers make; not yet: read-stats, the log-index export, Tor routing (`setTorEnabled`/`torStatus`/`setTorStorageDirs`), the served block window, or the storage-proof read (`getStorageProofJson`).

**Token balances (the apps' Query tab and Settings — Android, iOS, desktop).** An app-layer feature: it lives in the shared UI (`:ui`) and the hosts' own settings stores, and the engine contract is unchanged — the apps use the engine's generic verified `eth_call`, as any embedding wallet (e.g. the Freedom browser) does its own balance checks. An address lookup's result carries the address's ERC-20 balances, read with the engine's verified `eth_call` against the verified head (`VerifiedReads.callDetailed` on the JVM hosts, `IosRpcBackend`'s `myotis_eth_call_json` path on iOS; the `NodeController.ethCall` seam), and they are part of the result's Copy text. Which tokens: a short built-in list per network, pinned by contract address (`PopularTokens` in `ui/…/Tokens.kt`; mainnet, Gnosis, Sepolia), plus tokens the user adds by address, name and decimals in **Settings → Tokens**, stored per network (`Settings.customTokensJson`). A mixed-case address must pass its EIP-55 checksum; a custom token's decimals are checked against the contract's own `decimals()` — asked once per token per Query-tab session, later reads compare against that answer — and a mismatch is flagged with a one-tap fix; an empty reply is reported as "no token contract" rather than a zero balance, and `symbol()` is read as a `string` or a `bytes32` (MKR). The daemon has no token command.

**Validated:** MetaMask pointed at the device renders its confirm screen from verified balances, fees, and a local gas estimate, then broadcasts a real signed transaction — fully permissionless, no proxy. A Swarm Bee 2.8.2 full node ran against the Bee PoC build's `eth_getLogs`/state reads as its Gnosis RPC (postage events to the chain tip, chequebook exercised — [bee-rpc-service.md](bee-rpc-service.md)).

**Not implemented / rough edges:**
- `eth_subscribe`/WebSocket, ENS over JSON-RPC, and other less-common wallet methods (`-32601`).
- `eth_getProof` at a block other than the last 128 heads the node held (the current one included) or the finalized block, by number or by block hash (a hash is pinned to its block's attested root in one read of the anchor, ABI 47): a proof is pinned to the root of exactly the block named, and the engine holds no other block's state root attested (`-32602` below the head). A head the node missed (it was paused, or skipped it) is such a block; a header-chain walk per pinned block would cover those. A head a sibling chain replaced is not served for its number: each recent head's proven parent hash links it to the current head, and a head the ring cannot link (a skipped head or a replaced sibling above it) is confirmed against one header window anchored at the head first.
- **Endpoint security:** loopback only, no auth/rate limiting/TLS — sufficient for the same-device model; no opt-in path yet for a routable interface (would need auth/TLS first).
- A permanent engine refusal on the hosts' *state* reads still flattens to the retryable `-32000` in the one-block race between the router's window check and the engine's head (TODO.md); every refusal the router can decide is the permanent `-32602` (#366).
- JSON-RPC 2.0 envelope: an invalid request object is `-32600`; a notification (no `id`) is served but not answered; a batch carries at most 1000 requests (#366).

## 11. Log index — verified `eth_getLogs`
**Implemented (Rust engine only)**

An opt-in, per-network index of the logs of contracts the user chooses (the Expert-mode Index tab; `build-logindex` on the daemon), kept in `logindex[-net].db` under the data dir. Every stored log passed the anchored-header and `receiptsRoot` checks; a query outside the indexed coverage is an error, never a misleading `[]`. Per-entry `fromBlock` (walk back to each contract's deployment), a downward backfill that yields to head-follow, a head-gap bridge of up to 500,000 blocks, an optimistic tail above finality with reorg rewind, checkpointed final coverage that survives restarts, a pause switch and a "max download speed" mode, peers ranked by throughput. Removing a contract (the Index tab's Remove; `unwatch` in the config push, ABI 37) drops its entry, coverage and logs and leaves the other contracts' untouched. Portable, chain-tagged snapshots (`export-logindex` / `import-logindex`, the apps' import picker; format "MLIX" v2, names stripped on export and re-derived by verified reverse-ENS on import). Design: [eth-getlogs-design.md](eth-getlogs-design.md).

**Bounded trust carve-out (owner ruling 2026-09-25):** a *seeded* history of a root-committing protocol may be served on its publisher's word, because the client's on-chain root check keeps forged leaves out — [seeded-log-histories.md](seeded-log-histories.md). The engine has no dedicated seed path yet: a seed goes through the generic import and is served indistinguishably from walked logs, which is why the Bee and RAILGUN seeds stay demo-only. The verified alternative — downloadable bundles the walker re-verifies — is designed, not built ([logindex-verified-bundle-design.md](logindex-verified-bundle-design.md), #472).

**Not implemented:** the log index on the Java engine (`eth_getLogs` answers `-32000` there; the Index tab hides when the Java engine is forced); `eth_getLogs` on the iOS host (its RPC backend has no `getLogs`, so the method answers `-32000` there too — the JVM hosts wire it, and the Node addon exports it since #503); the Node addon's log-index export; provenance marking of seeded ranges.

## 12. Privacy — Tor routing
**Implemented, feature-gated and experimental (Rust engine; desktop and Android hosts)**

`-PtorEngine` links Arti into the Rust engine; a Settings toggle (desktop and Android — the Android jniLibs run Arti on rustls/ring and the host names Arti's storage directories; not iOS yet) routes **account reads** (`get_account` — balance/nonce, and the account half of a code read) over per-address isolated Tor circuits and **the broadcast of the wallet's own transactions** (and their rebroadcasts) under a fresh isolation token per send, both with ephemeral RLPx keys, failing closed with no clearnet fallback; a send that went over Tor is never pushed from the real IP again (not rebroadcast, not re-pushed on a wallet's re-submit). Storage, `eth_call`, blocks, receipt polling, the CL fetch and discovery stay on the real IP, and the Tor reads and sends go only to the persisted Tor reserve — about a third of the verified peers (at most 24), moved out of the peer cache while Tor mode is on and never dialed directly again, ready ten minutes after their last direct contact (none ready → fail closed), with a Tor-side Hello that says `myotis` without the version — a first step toward the quarantined pool the design describes, not all of it. A finalized read over Tor is refused. Design, threat model and the validated proof of concept (`rust/tor-poc`): [privacy-and-tor.md](privacy-and-tor.md).

## 13. Balance watch — the Watch tab
**Implemented (native currency and ERC-20 tokens; Android and desktop)**

The user lists addresses per network. The app checks their **verified** balances — the native currency, and each token Settings → Tokens lists, by verified `eth_call` to `balanceOf` (#639's read; an empty reply is an error, never a zero). An unverified read or one anchored at an older block changes nothing; a token observation is anchored to the block its `eth_call` ran against (`CallResult.blockNumber`, both engines). Android checks while the app is in the foreground, and — plugged in on an unmetered network — right before the idle controller puts a stack to sleep, after a catch-up pass has woken one, and every 10 minutes while "Stay awake while charging" keeps it running. The desktop checks every 5 minutes while it runs. A change posts a notification and joins the tab's list. A scan of up to 64 blocks newest first (16 on a metered network) names the transactions from or to the address, or a fee-recipient credit; a token change's scan reads the blocks' receipts (64, or 8 on a metered network) for the token's `Transfer` logs, and a wrapped native token's `Deposit`/`Withdrawal`. When it finds none, the text says what moves funds without one (a contract, a validator withdrawal, a bridge; for a token, a rebase such as stETH's), or that the gap was wider than the scan. Design and schedule: [balance-watch.md](balance-watch.md).

**Not implemented:** iOS (no Watch tab: the C-ABI reader and the notification permission are not written); internal transfers named by their contract call (no engine serves traces); withdrawals named (no engine's block JSON carries the verified list); a ranged block read for the scan (each block read fetches its own header window up to the anchor).

| 13. Balance watch (Watch tab)        | **Implemented** (native + ERC-20; Android, desktop) | No iOS host; a gap wider than the scan names no transaction |

The core verification pipeline (sync committees → state root → Merkle proofs → local EVM) is functional end-to-end in both engines, exposed as a verified JSON-RPC endpoint on every host, and used by a stock MetaMask to read, estimate and **send a real transaction** on a phone, by a Swarm Bee node as its chain RPC, and by embedders through the Node.js addon and the iOS frameworks. The biggest remaining work: historical-block verification (accumulators), the seeded-history provenance / verified-bundle path for deep log histories, and the Java engine's feature lag behind the Rust engine (or its retirement).
