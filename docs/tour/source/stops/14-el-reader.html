myotis-net, part 6: the verified reader

ElReader is where the execution layer comes together. It combines discv4, the peer pool and the beacon-fed ExecAnchor into verified wallet reads (accounts, storage, proofs, code, eth_call and friends, ENS, blocks, receipts, fees, transactions), the transaction send path, and the engine behind the eth_getLogs index. Since September the file has more than doubled, to 18,846 lines. Most of the growth is new subsystems: a per-head fee memo with a background follower, an address-activity follower that reads block access lists, a judged and Tor-capable send path, finalized-state reads, and a log index that survives restarts with a finality claim. Read it with the section map. This stop is about how it is built: which lock guards what, which tasks own what, and how work is cancelled.

What changed since September

The old tour read this file at 8,914 lines. The structure it described is still there (configuration, result types, hedging, the struct, construction, state reads, EVM reads, blocks, writes, receipts, the log index, tests), but each part grew and several new parts arrived:

  • Finalized reads. Most reads take a ReadAnchor (Head or Finalized). A finalized read is proven against the beacon-finalized state root with no fallback to any other root. eth_getProof (get_proof) is new.
  • More EVM entry points. eth_call for a full transaction object, eth_createAccessList, trace_call and simulate, all on the same setup.
  • The send path judges and detaches. send_raw_transaction refuses non-transactions and other chains' transactions, refuses a transaction the sender provably cannot pay for (a pre-broadcast check on fresh, verified state), answers at the first peer write that lands (first_accepted), and in Tor mode sends only over Tor.
  • The fee memo. Fee reads are answered from a per-head memo, kept fresh by a fee follower task, with single-flight computes and bounded waits.
  • The address-activity follower (#691) keeps verified headers for watched addresses and answers some account reads from block access lists (BALs) with no peer request at all.
  • Peer bookkeeping in races. A hedged race now also reports peers the winner outpaced, and block/receipt reads defer strikes during tip lag.
  • Log index. Receipts-first candidate fetches, a separate chunk sizer for the head side, unwatch, a restart finality claim, and many more pure policy functions with their own test modules.
  • Pause and resume. ElCarry carries the node key and pool memory from a paused reader to the one that resumes it.

One ElReader per hosted chain. It owns a discv4 service and a snap/eth PeerPool, and shares the light client's ExecAnchor, the only trust bridge from consensus to execution. State reads check Merkle-Patricia proofs against a state root, then tie that root to the beacon chain (stateRootMatch or headerChain). An unverifiable state read still returns Ok, with the reason in fail_reason. Block, receipt, fee and transaction reads check that a header window hash-links to a beacon-anchored block (the optimistic head, or the finalized block), then check the trie roots. For those reads, returning a result at all is the verification. The file also holds the send path and the whole log-index engine.

domain The module doc still describes the five-step state-read ladder. Step 2 is new since September: a read picks either the optimistic root (head read) or the finalized root (finalized tag). The doc explains why a finalized read can fail: geth keeps about 128 recent states, and finality trails the head by 64–96 blocks, so a finality delay pushes the finalized state out of what peers still hold.

The struct: a map of the memory model

Hosts hold the reader as Arc<ElReader> (host.rs keeps an Option<Arc<ElReader>> per running chain). ElReader is not Clone, and almost every method takes &self. So every field that changes after construction is behind something that allows mutation through a shared reference: a mutex, an atomic, a semaphore. In Java terms, every field is final, and the mutable ones are final references to synchronized objects. Sorted by the kind of guard:

  • interior-mutability smart-pointers The cancellation pair. request_shutdown is a tokio watch::Sender<bool>: every registered operation subscribes to it. requests holds Weak<Operation>s, so the registry never keeps a finished request alive. Only stop() upgrades them, to wait for the live ones.
  • interior-mutability concurrency tx_scans: std::sync::Mutex<TxScanMap> nests the two mutex kinds. The outer std lock guards only the map and is held for a few statements. Each entry is an Arc<tokio::sync::Mutex<TxScanState>> that serialises the slow network scan for one transaction hash, so different transactions proceed in parallel.
  • modules-cargo #[cfg_attr(not(feature = "tor"), allow(dead_code))] applies an attribute only when a condition holds, here to silence a warning in non-Tor builds. Its comment is still stale: eth_cfg is read outside Tor code too (the restart-claim chain tag, ENS naming, a log line).

interior-mutability log_index_write: std::sync::Mutex<()> guards no data. Its guard means “a checkpoint write is in progress”. The documented lock order (before log_index, never after) prevents deadlocks: two threads that take the same two locks in the same order can never each hold the one the other waits for. Java has no direct equivalent of a mutex that protects nothing; the nearest is a dedicated Object used only for synchronized blocks.

  • async interior-mutability log_index_drive is an async mutex held across network awaits, so two coverage-advancing ticks (the background appender and an on-demand fill from a host thread) never interleave. A std guard held across an .await would block a runtime worker thread, and tokio would not be able to run other tasks on it meanwhile.
  • smart-pointers async fee_estimate_compute is an Arc<tokio::sync::Mutex<()>> because a read hands its owned guard (OwnedMutexGuard) to a spawned compute. An owned guard keeps its own Arc to the mutex, so it has no lifetime tied to &self and can move into a 'static task.
  • concurrency Each background task sits in a std::sync::Mutex<Option<JoinHandle<()>>> slot: Some while it may run, take()n by the stop path to abort it.

Construction

ownership ElConfig { cache_path, ..base } is struct-update syntax: take cache_path from the local, and every other field from base. It moves those fields out of base, so base cannot be used afterwards (Kotlin's copy(cacheField = …) copies instead). carry.key and carry.pool are moved out of carry the same way. ElCarry (line 11451) is what a pause leaves for the resume: the clearnet node key and the pool's dial verdicts, so neighbours do not have to bond with a new node id after every wake.

  • concurrency Earlier in start_inner, mpsc::channel(256) is created: discv4 gets the sender, and the pool gets the receiver (rx here), a stream of candidates to dial.
  • smart-pointers iterators-closures Some(Box::new({ let anchor = Arc::clone(&anchor); move || anchor.optimistic_head() })): a block expression clones the Arc first, and the move closure then owns that clone. The original anchor is still available below (start_anchor_resolver, the struct literal). The boxed closure becomes the pool's head source.
  • async request_shutdown: tokio::sync::watch::channel(false).0 keeps the sender and drops the first receiver at once. That is fine: receivers are created later with subscribe(), and cancel_requests uses send_replace, which stores the value even when no receiver exists (plain send would return an error then).

Request budgets and stop

async smart-pointers Every host-facing read runs inside request(): a 90 s Operation (request::REQUEST_BUDGET) registered weakly in requests (see request.rs). The future is passed by value as impl Future: the operation owns it, and dropping it at the deadline cancels it. request_with_budget is the same with another budget; the fee follower, the detached pre-broadcast read and ENS use it.

  • async The order matters. First the shutdown flag, so every registered operation and every follower sees it. Then the three producers are aborted and awaited, so none of them starts new work while the requests drain. Then each live request is upgraded from its Weak (filter_map(std::sync::Weak::upgrade)) and awaited to settled(). Then the appender slot is aborted once more, without awaiting, in case something started it again during the drain. Then the final, unthrottled checkpoint, and only then the pool and discovery.
  • error-handling self.requests.lock().map(…).unwrap_or_default() treats a poisoned lock as an empty list instead of panicking. The workspace builds with panic = "abort", so a panic would kill the host app.

Background tasks: the appender and the followers

  • smart-pointers ownership self: &Arc<Self> is an explicit receiver type. The method needs the Arc itself to call Arc::downgrade(self); a plain &self is a reference to the ElReader inside the allocation and cannot produce a Weak. Callers must hold an Arc<ElReader> to call it.
  • smart-pointers async A Weak in a spawned task. A strong Arc captured by the task would keep the reader, and all its networking, alive for as long as the loop runs. weak.upgrade() yields a strong Arc for one tick, or None once every strong reference is gone, which ends the loop. The comment still justifies this with an Arc::try_unwrap teardown that no host uses any more (host.rs calls reader.stop().await). The Weak is still right: it means a host that drops the reader without calling stop() does not leak a running appender.
  • async error-handling rt.spawn on an explicit runtime Handle, because this synchronous method may be called from an FFI thread, where a bare tokio::spawn would panic (no runtime), and a panic means an abort.
  • async interior-mutability let _drive = reader.log_index_drive.lock().await; inside a block: the async guard is held across the append tick's awaits and released at the block's }, so the backfill step and the naming pass run outside it. _drive is a real binding; the pattern _ alone would drop the guard at once.

async The on-demand fill takes the same log_index_drive lock, re-checks coverage under it (another caller may just have filled it), and runs one append tick. tokio::time::timeout(…, fill) drops fill after 5 s. Dropping a future at an .await is safe here because, as the comment says, coverage only changes synchronously under the index lock, never half-way through an await.

The fee follower (ensure_fee_follower, line 8340) and the activity follower (ensure_activity_follower, line 8513) use the same shape: a task slot, an idempotence check with is_finished(), a Weak that is upgraded per tick, and a tokio::time::interval with MissedTickBehavior::Delay. Two differences: they use Handle::try_current() and quietly do nothing outside a runtime, and they check request_shutdown first, so a read racing stop() cannot restart them. Both end themselves when their demand goes away (no fee reads being polled, an empty watch list), and the next read or push respawns them.

  • interior-mutability iterators-closures self.activity.lock().map(|s| { … }): lock() returns Result<MutexGuard, PoisonError>, and map moves the guard s into the closure. The guard is dropped when the closure returns, so the lock is held only for that expression, and set_bal_demand(false) runs under it on purpose (a push refilling the list must win).
  • enums-patterns s.is_active().then(|| s.top()) turns a bool into an Option; together with let Ok(top) = … else and let Some(top) = top else the tick separates “lock poisoned”, “list empty” and “nothing kept yet” (top is itself an Option).
  • concurrency for slot in [&self.activity_task, &self.activity_bal_task] iterates an array of two references. The follower is stopped first, so it cannot spawn a new BAL pass after the BAL slot is emptied.

Hedged reads

  • traits-generics async A generic async higher-order function: make: impl FnMut(P) -> Fut with where Fut: Future<Output = Result<T, String>>. Every async move block has its own anonymous type, so there is exactly one push site into the FuturesUnordered. Two different blocks could not share the collection without boxing.
  • async make(…) only creates a future; nothing runs until it is polled. scope_send_marker wraps it in a tokio task-local scope that records when the request frame actually left (a OnceLock<Instant> shared through an Arc); that timestamp decides who was outpaced. The wrapper async move { (idx, fut.await) } owns the future and tags the result with the peer index.
  • async select! races the next completed attempt against a fresh sleep(delay), created anew on every loop pass, so the hedge timer restarts whenever an attempt finishes. The if guard disables the timer arm when no more peers may be started, and else => break handles “all branches disabled”.
  • async ownership Cancellation by drop. return out; drops in_flight, and with it every attempt still running. There are no cancel() calls; in Java you would call future.cancel(true) on each. The doc comment above warns that a dropped attempt can leave that peer's writer torn (it condemns the connection), a price paid only once the answer is in hand. For the same reason the losers are not polled again after the winner arrives.
  • enums-patterns out.fallback.get_or_insert(value) keeps the first non-accepted answer as a fallback.
  • modules-cargo #[cfg(feature = "tor")] on an if statement: in Tor builds with Tor switched on, the read goes over an isolated Tor circuit instead (get_account_over_tor, line 6366), with no hedging. It fails closed: no ready Tor peer means an error, never a clearnet fallback. Finalized reads are refused under Tor.
  • borrowing async |peer| async move { self.get_account_from(&peer, address, fin).await }: the future borrows self. That is fine because the race is awaited inside this method and never spawned, so no 'static bound applies. address ([u8; 20]) and fin (Option<FinalizedExecution>, which derives Copy) are copied into each future. That is also why the closure can be FnMut: it gives nothing away when it is called.
  • traits-generics Four closures, four roles: accept ends the race (a verdict, or a global failure such as “beacon not synced” that no other peer could fix); served says whether that answer earns credit; excused forgives a finalized read's empty proof (the peer is not obliged to keep an old root); the last is the label for error messages.
  • domain Only a verified head read feeds the shadow cache (read_stats.observe_account). get_account_following, which calls this, first tries the activity follower and, after a verified head proof, seeds it (seed_followed): a watched account can then be answered from verified block access lists with verifyMethod blockAccessList and no peer request.

domain hedged_read (line 5988) applies the outcome to the pool: misses that were not excused are banked as failures (witnessed only if another peer served), outpaced peers are reported with record_snap_outpaced, and the winner gets record_snap_served only if its answer was a serve. Block and receipt reads use settle_pool_race instead, whose tip-lag arm hands strikes back to the caller unbanked, so a retry that succeeds strikes nobody.

EVM reads

  • async concurrency The sync-to-async bridge from the reader's side. snap_oracle runs in async code, so Handle::current() works, and it stores the handle in the oracle. Then request::blocking(move || …) moves the executor, calldata, context and overrides onto a blocking thread, where the oracle's block_on is legal. blocking limits native work to 8 slots with a bounded FIFO wait, and the closure must be Send + 'static, which the move provides.
  • error-handling enums-patterns The ? after .await covers only blocking's own failures: no free slot, a cancelled or expired request, a join error. joined is the EVM's Result, which call_answer maps into a CallOutcome and labels with the block hash only if the call actually ran.
  • smart-pointers traits-generics Unsizing coercion. Arc<InMemoryStateProofCache> becomes Arc<dyn StateProofCache> at the constructor call. Binding the concrete clones to variables first matters: Arc::clone(&x) written directly in a dyn-typed position would be inferred as Arc::<dyn …>::clone and fail to type-check.
  • domain evm_setup_at picks the head or the finalized header. The finalized header comes over a window anchored at the finalized block itself and is then cross-checked against the anchor's own hash and state root (finalized_header, line 7581).

The header trust gate

  • domain error-handling “The sole gate that turns peer-supplied headers into trusted ones”, with seven callers. The window must have the exact length, start at the requested number, end at the anchored hash, and be parent-linked throughout. New since September: the anchor is a WindowTop, either the optimistic head or the finalized block. A read at or below finality anchors at the finalized block, which every roughly synced peer holds, so it no longer depends on the head.
  • error-handling The error messages differ on purpose. A short window looks like tip lag (the peer has not imported that far yet, so a retry is reasonable), while an over-served window is a protocol violation. all_tip_lag (line 676) string-matches these messages, and the comment there names the coupling.
  • enums-patterns top.number().checked_sub(from).map(|span| span + 1) with let Some(count) = … else: subtraction that would underflow becomes None instead of wrapping (in release builds) or panicking (in debug builds).
  • domain Only a head-anchored window counts as proof of the peer's head (note_head_served), which the read ladder then ranks peers by.

Writes: judged, detached, and Tor-only in Tor mode

error-handling domain Three refusals before anything goes out. Bytes that are not a sendable transaction, and a transaction signed for another chain, are SendError::Refused (hosts answer the permanent -32602). A transaction the sender provably cannot pay for, or whose nonce is used, is Rejected in geth's own words, so wallets classify it as they would geth's. The method takes self: &Arc<Self> because the pre-broadcast check spawns a task that needs its own Arc.

  • async smart-pointers Detached, not cut. The account read is tokio::spawned, so it must be 'static: it gets its own Arc (let reader = Arc::clone(self)) and an owned semaphore permit (try_acquire_owned on an Arc<Semaphore>). timeout(ACCOUNT_READ_BUDGET, read) wraps the JoinHandle. When it expires, the handle is dropped, and dropping a JoinHandle does not cancel the task; it only detaches it. Contrast hedged_race, where dropping the futures cancels them. The comment says why it matters: a read dropped mid-request can tear the connection the broadcast is about to use.
  • concurrency let _permit = permit; moves the permit into the task, so it is released when the task ends, whenever that is. At most send_check::DETACHED_READS_MAX such reads run; past that, the send goes out unchecked. The detached read is still registered via request_with_budget, so stop() cancels and drains it.
  • error-handling joined.unwrap_or_else(|e| Err(…)) flattens the JoinError (the task was aborted) into the read's own Result. Every reason not to judge becomes PreBroadcast::Unchecked, and the send goes out as before: the check only ever adds refusals on proven state.
  • async ownership first_accepted spawns every write as its own task (hence Fut: Send + 'static) and returns at the first success. The raw transaction is shared as Arc<[u8]>, one allocation for all peers, each task holding a clone. Each task's select! has three arms: the write, “another write landed, then grace elapsed”, and shutdown. So writes are never cut before one has landed, and are cut grace after.
  • concurrency drop(tx) after the loop is load-bearing. rx.recv() returns None only once every sender is gone; the tasks hold clones, and this local original would otherwise keep the channel open forever. A watch channel (landed) broadcasts “one landed” to all tasks; subscribe() gives each its own receiver.
  • interior-mutability borrowing matches!(self.sent_txs.lock().unwrap().bytes.get(&hash), …): the MutexGuard is a temporary, dropped at the end of the let statement, before the .await on the next lines. That matters: a std guard alive across an .await would make the future non-Send.
  • interior-mutability borrowing Collect under the lock, act outside it. Each let x = { let mut g = m.lock().unwrap(); …; value }; block drops its guard at the }. The network sends happen with no lock held.
  • modules-cargo #[cfg(not(feature = "tor"))] drop(over_tor);: without the Tor feature the Tor branch is compiled out, so this explicit drop is the only use of over_tor and keeps the build free of an unused-variable warning.
  • async ownership The clearnet rebroadcast is a detached tokio::spawn that must be 'static, so it owns everything: work: Vec<Vec<u8>> and peers: Vec<Arc<ManagedPeer>> are moved in. The wallet's receipt poll triggers the rebroadcast but never waits for it. Each send is bounded by a 5 s timeout.
  • error-handling .lock().unwrap() here vs if let Ok / map_err elsewhere: two lock-poison styles in one file. A lock is poisoned only when a thread panics while holding it and the program keeps running. Under panic = "abort" that cannot happen, so these unwrap()s cannot fire in production.
  • smart-pointers concurrency A drop guard for a flag. TorRebroadcastGuard::claim uses compare_exchange(false, true, …): it succeeds for exactly one caller while the flag is clear, and returns a guard whose Drop clears it. The guard is moved into the spawned task (let _guard = guard;), so the flag stays set until that task ends, or is dropped, however it ends. Java would need a try/finally around the whole round.
  • domain A Tor rebroadcast round walks on through the pool: round.wrapping_mul(TOR_MAX_CANDIDATES) is the offset into the eligible peers, so each round reaches peers the earlier ones did not. Only target identities go into the task, not the pool's peer handles; each push is a fresh Tor stream with an ephemeral key. A send that first went over Tor is never pushed from the real IP (rebroadcast_route).

interior-mutability smart-pointers The receipt scan's per-transaction cursor. st.try_lock() inside retain: an entry whose tokio lock is currently held is in use, so it is kept regardless of age. Arc::clone(scans.map.entry(tx_hash).or_insert_with(…)) returns a handle to the per-transaction mutex, and the caller (locate_mined_tx) locks it after this function has returned and the map guard is gone. map_err(|_| "engine lock poisoned")? turns poison into an error rather than a panic.

The fee memo: single flight, bounded waits

Fee reads (eth_gasPrice, eth_maxPriorityFeePerGas, eth_feeHistory) used to compute on every call, up to the 90 s budget, while wallets give up after about 10 s. Now fee_estimate looks in a per-head memo (el::feecache). A fresh hit is returned. A stale hit (a previous head's value) is returned raised by the most the base fee can have grown since (12.5% per block). Only a miss starts a compute.

  • async smart-pointers Arc::clone(&self.fee_estimate_compute).try_lock_owned() either takes the single-flight lock now, as an OwnedMutexGuard, or fails at once. The winner moves the guard into its compute (move |r| async move { … flight … }); everyone else waits for the result instead of queueing behind the lock.
  • traits-generics async bounded_fee_compute takes F: FnOnce(Arc<Self>) -> Fut + Send + 'static. The closure is 'static because it is moved into tokio::spawn; its future Fut need only be Send, because it is created and awaited inside the task. The compute receives its own Arc<ElReader> (r) instead of borrowing &self, which a 'static task could not hold. await_bounded then waits at most 5 s; giving up drops only the JoinHandle, and the compute runs on to fill the memo for the next poll.
  • concurrency async No lost wake-ups. wait_for_fee creates the notified() future, pins it (tokio::pin!, because Notified must not move once registered) and enables it before it checks settled(). notify_waiters stores no permit, so a store that landed between the check and the await would otherwise be missed, and the read would sleep until its deadline. Java's Condition.await has the same trap, solved by checking under the lock.
  • ownership async Drop order as a design tool. Locals are dropped in reverse order of declaration, and an async fn's parameters are bound before its body, so they are dropped after its locals. on_drop is a local and _flight a parameter: if this future is dropped mid-ladder (a budget cut, a stop), on_drop records the failure and wakes the waiters before the single-flight lock is released. A caller queued on that lock then sees “just failed” and does not rerun the ladder.
  • lifetimes traits-generics FeeFailOnDrop<'a, F: Fn(&mut FeeCache)> borrows the reader for 'a and stores the recording closure by value; it is a stack guard, never stored or spawned. disarm() on the success path turns the Drop into a no-op, like a Java finally with a “completed normally” flag.
  • concurrency _flight is named, so the guard lives until the function returns. A parameter written as _: OwnedMutexGuard<()> would drop it at once.

The log-index engine

domain A 6 s appender task keeps the index current along four paths. (1) A finalized per-block appender. (2) A head-gap bridge that takes over when the gap exceeds APPEND_WINDOW (128 blocks) or the edge has not moved for three ticks; it first walks down from the finalized anchor, then back up, and its BridgePlan is take()n out of a std mutex before the network I/O and put back afterwards. (3) An optimistic tail above finality, the only part that can reorg; it keeps its own (number, hash) record and rewinds on a mismatch. (4) A descending backfill, with peers ranked by measured throughput and chunk requests pipelined through futures::StreamExt::buffered. New since September: candidates fetch receipts first and bodies only for blocks that hold a watched log; the head side has its own chunk sizer; entries can be unwatched; and a checkpoint records a finality claim, so a restart keeps coverage it proved final instead of re-walking it.

  • interior-mutability concurrency let Ok(_writing) = self.log_index_write.try_lock() else { return false; }; skips instead of waiting: whoever holds the lock is writing a newer snapshot anyway. try_lock returns Err both for “held” and for “poisoned”, and both mean skip here.
  • interior-mutability The (bytes, clamp) block serialises under the index lock and releases it at the }, before the slow write and fsync, so the appender, the walker and every eth_getLogs are not blocked by the disk. Lock order inside: checkpoint lock, then index lock, then (in checkpoint_clamp_for) the tail and claim locks.

interior-mutability error-handling unwatch_log_index (line 2902) shows the same order with a twist. It first answers the common “nothing to drop” case under the index lock alone, so a repeated unwatch does not queue behind a multi-gigabyte import holding the checkpoint lock. Only then does it take the checkpoint lock and the index lock again, in the documented order, and re-read the state under both. The “unwatch owed” atomic is set before the write attempt, so no outcome can leave it unset; the write that lands clears it.

  • traits-generics async Async methods in a trait. The trait declares fn receipts(&self, …) -> impl Future<Output = …> + Send (return-position impl Trait in a trait), and the impl writes plain async fn. The explicit form is what lets the trait promise + Send, which the spawned appender task needs; a bare async fn in the trait could not say that. The trait exists only so fetch_candidate_logs can be tested against a scripted peer.
  • traits-generics trait CandidateSource: Sync is a supertrait bound: every implementor must be Sync, so a &P may be held across awaits in a Send future.

lifetimes async ChunkFetch<'a> (line 10804) is a BoxFuture<'a, …>: a heap-allocated, type-erased, Send future that may borrow for 'a. The comment explains why the loop boxes instead of writing chunks().map(|c| async move { … }): a closure returning a future that borrows the header slices is “not general enough” over their lifetime for the spawned task's Send bound, a known limitation of how the compiler checks such closures. buffered(depth) then polls up to depth fetches at once and yields results in order, which the truncation logic depends on. Dropping the stream on a failure cancels the fetches still in flight.

error-handling traits-generics From impls decide what a bare ? means. In the backfill batch every String error becomes a peer-blamed failure, so the few failures that are the engine's own fault are built explicitly with BackfillBatchError::ours. Compare FeeBuildError (line 1944), which deliberately has no From<String>: there, a ? on a plain String error fails to compile, so every site must state whose fault it is. A wrongly blamed check once struck every snap peer on every fee-history build.

domain testing The restart claim, as one pure function. After a restart the beacon store resumes from a snapshot written once per sync-committee period, so its finality can sit hours below a checkpoint this node already proved final. The claim (RestartClaimState, under log_index_claim) lets the tail hold that coverage instead of rewinding it. It ends when the anchor catches up (Subsumed), or when a current finality verified after the claim was first weighed sits more than 512 blocks below it (Contradicted). Decisions like this one are free functions marked “Pure — unit-tested”, so the tests need no peers; restart_claim_reader_tests goes one step further and starts an offline ElReader with no bootnodes.

Testing on a virtual clock

  • testing async #[tokio::test(start_paused = true)] runs the test on tokio's paused clock: when every task is waiting on a timer, time jumps forward instantly. started.elapsed() can then be asserted exactly (4 s, 20 ms) in a test that takes milliseconds. This needs tokio's test-util feature, which myotis-net enables only for dev builds (Stop 2).
  • testing let (_stop, shutdown) = watch::channel(false); keeps the sender alive in _stop. Writing let (_, shutdown) would drop the sender at once, and first_accepted treats a dropped sender as a shutdown, so every write would be cut. The broadcast_pushes tests solve the same problem with std::mem::forget(tx).
  • traits-generics testing fn flags<const N: usize>() -> [Arc<AtomicBool>; N] is a const generic: the array length is a type parameter, inferred from the destructuring pattern let [quick, inside, outside, wedged] = flags();. std::array::from_fn builds each element.
