The trust chain, top to bottom

A verified state read asks a snap peer for an account or a storage slot at some state root, together with a Merkle-Patricia (MPT) proof. The proof only shows that the value belongs to that root. The question this stop answers is why you may believe the root. The only things the engine trusts are the light client's sync-committee signatures (Stop 10) and two embedded accumulators. Everything else must be linked to them by hashes.

The link has three forms. The fast path: the peer's root is one the light client already recorded, so stateRootMatch. The header chain: fetch the headers from the peer's block up to the newest attested block; the newest one must hash to the attested block hash, each header must hash to its child's parentHash, and the oldest must carry the peer's root, so headerChain. And, for a read pinned to finalized, the proof is checked against the finalized root itself.

What changed since September

The header walk used to start at the finalized block and climb to the peer's block. That direction was unsound: a peer could name the real finalized block as the parent of a header it made up, with any state root, and the chain verified. The walk now ends at the optimistic head and checks the newest hash, and verify.rs carries a test for exactly that attack. Also new: the Gloas pending-hash path in the anchor, a ring of 128 recent heads, a five-second FIFO wait in front of the EVM slots, three new files (fork_watch.rs, readstats.rs, getproof.rs), and a pool that has nearly tripled in size (head-aware ranking, head probes, lagging eviction, scarcity backoff, DNS seeding, a BAL hunt and a Tor reserve).

Gives every host-level execution-layer operation a managed lifetime: a deadline (90 s by default, never later than a parent's or a native caller's), a cancellation flag, a parent link, and a count of the blocking jobs it started. run and run_registered execute a future in that scope. When the future ends, or its deadline or a cancel fires, they cancel the scope and then wait until every blocking job has actually returned, because a started spawn_blocking closure cannot be killed. blocking is the single door into tokio's blocking pool for EVM work: 8 jobs run at once, up to 32 more wait in a FIFO line for at most 5 s, and anything past that is refused. The module doc says: “Permits belong to jobs, never to the caller's patience.”

The light client's only hand-off to the execution layer, which its doc calls “the only thing the EL trusts”. It holds the finalized execution block (slot, number, state root, hash, timestamp), the optimistic head with its parent hash, a window of up to 8192 BLS-attested (slot, state_root) pairs for the fast path, and a ring of the last 128 optimistic heads for eth_getProof and EIP-1898 block-hash pins. Since Gloas (EIP-7732) a light-client header proves only an execution block hash; the anchor then records it as pending, and adopts a header only when the keccak of its RLP is that hash. sync.rs (Stop 10) writes it, and every verified read consults it.

The execution-layer peer pool keeps a live set (target 8) of snap-capable ManagedPeers for verified reads. It dials candidates from four sources (pinned enodes, the persisted peer cache, discv4 and, since #539, EIP-1459 DNS trees) through the RLPx and eth handshake with at most 16 dials in flight, and records each outcome in an address backoff, a node-id blacklist or the peer cache. It ranks peers for each read, benches a peer that fails one, strikes and evicts one that keeps failing or lags behind the anchored head, and hunts harder when nobody can serve. Up to four background loops run: the dialer, a 10 s maintainer, a 1 s start-up prober that gives up after its first minute with a head, and (Gloas) the anchor resolver. Around them sit newer duties: block access list (BAL) servers for address activity (#691), the eth/69 served-header backfill, and a Tor reserve of peers it never dials directly.

Picking: the read ladder

  • traits-generics enums-patterns A derived Ord as policy. #[derive(PartialOrd, Ord)] on a struct compares fields lexicographically in declaration order, and false < true. So the field order is the ranking: a peer that says it is behind goes last, then benched peers, then by Coverage (whose own derived Ord is Covers < Near < Unknown < Behind, declared in peer.rs), then unproven peers. In Java you would write a Comparator.comparing(…).thenComparing(…) chain.
  • iterators-closures ladder_order sorts indices, not peers: order.sort_by_key(|&i| keys[i]). The closure copies each LadderKey (it is Copy). sort_by_key is stable, so ties keep the newest-connection-first order the caller passed in.

borrowing smart-pointers async newest_first: Vec<&PooledPeer> borrows through the tokio guard peers. The function returns owned Arc::clones, so the guard is released when the function returns, before any caller does network I/O. Every peer stays in the list: a benched or lagging peer moves to the back, never out, so the sole server remains reachable.

Scoring: bench, strike, evict

domain A read failure benches the peer for 30 s (READ_FAIL_BENCH) and banks a strike; three in a row evict it (READ_FAILS_EVICT). The sole remaining peer gets no strike at all, not even a banked one, because a failure against the only server is probably our own stale request, and a banked strike would evict it the moment a second peer arrived. Being pure, the rule is tested without a network. A related rule: an outpaced peer (silent while a hedged read was answered by another) is benched, and from its second outpace in a row each outpace also counts as a failure, so a dead but open connection is eventually evicted (lines 380–396).

macros modules-cargo const _: () = assert!(…); is a build-time assertion: the expression is evaluated by the compiler, and tuning the peer cache's threshold without this one fails compilation. The comment above it explains why they must be equal: the live strike and the persisted cache strike then move in lockstep, so an evicted laggard is marked Denied in the same beat.

enums-patterns domain Witnessed or not (#465). A failure is Failed when another peer served the same read, and FailedUnwitnessed when nobody did. Both bench and strike in the live pool, so it still rotates. Only a witnessed one may reach the persisted cache, and then only while another peer is live (persist_verdict). A cold pool once turned 14 of 27 cache entries into snapbad verdicts with failures that were really about our own request. QualityOutcome::failed(witnessed) is an associated function used as a small constructor.

  • async interior-mutability Locks taken one at a time. prune_closed locks peers itself, so it runs before this function takes the lock: tokio's Mutex is not reentrant, and locking it twice in one task deadlocks. On the evict path the guard is dropped explicitly with drop(peers) before the next .await locks backoff and then attempted.
  • concurrency Ordering as a correctness argument. The evicted address stays in attempted until its backoff is recorded. A concurrent try_dial checks the backoff first and the claim second, so it can never see the address as neither backed off nor claimed and re-dial it in the gap.
  • borrowing if let Some(p) = peers.iter_mut().find(…) holds a mutable borrow of one element. Inside the evict branch, peers.iter().find(…) and peers.retain(…) use the vector again; that compiles because p is not used after the borrow checker's last use of it on that path (non-lexical lifetimes). return self.persist_quality(…).await; returns the unit value of the awaited call.
  • domain shields_bal_server: while a host follows address activity, the pool's one recent BAL server is benched rather than evicted. Its BALs are checked against header commitments, so the worst it can do is withhold, which ends the shield after 5 minutes.

Dialing and admission

  • smart-pointers lifetimes concurrency Owned permits. tokio::spawn (here via inner.tasks.spawn) needs a 'static future, which may not borrow the semaphore. acquire_owned() on an Arc<Semaphore> returns a permit that holds its own Arc, so it can move into the task. drop(permit) after the dial is semaphore.release() in a finally; it is also released if the task is aborted. Contrast request.rs, whose static semaphore gives a 'static borrow for free.
  • borrowing async if let Some(b) = backoff.get(&addr) borrows an entry; after the if b.blocks(…) test, b is dead, so backoff.remove(&addr) on the same map compiles. The { … } blocks release each tokio guard before the next lock. The live count is read before the backoff lock, never under it.
  • smart-pointers let _stamp = DirectContactOnDrop(pubkey); is a guard whose only job is its Drop: when the dial task ends, returned or aborted, it stamps a direct contact with that node. The Tor path waits ten minutes after such a contact before reaching the same node, so a peer cannot pair our IP with a Tor read by timing (docs/privacy-and-tor.md).
  • enums-patterns DialVerdict separates Skipped, Dialed and Shutdown; try_dial folds it to the old bool with != DialVerdict::Shutdown, and the scarcity re-dial counts only real dials.

bytes-strings domain Classifying by prefix, not substring. A peer's client id is echoed into some error strings, so contains could be steered by a hostile peer; starts_with on a producer-written prefix cannot. A wrong chain gets the node id blacklisted and a 10-minute backoff; TooManyPeers (Disconnect reason 4) gets 60 s, or 30 s while the hunt is engaged; anything else 30 s. Earlier arms of the same match refuse a snap peer whose announced head trails the anchored one by more than 32 blocks (refusing_lag, a 10-minute lagging backoff, no cache strike), and pool the rest with a fresh ManagedPeer::spawn_serving.

Backoff that shrinks with the shortfall

domain enums-patterns Since #539, a backoff window is not fixed. Below target it shrinks to window × live / target, clamped between a floor and the full window: a pool holding 2 of 8 re-dials a 10-minute laggard after 2.5 minutes. The floors come from geth: it closes a second inbound connection from the same IP within 30 s (PEER_INBOUND_THROTTLE), so nothing is re-dialed sooner. A wrong-chain window returns None from scarcity_floor and never shrinks. div_ceil rounds the per-tick dial budget up, so one peer short still costs one dial a tick. Duration::mul_f64 scales a duration by a float.

Shared state and the loops

  • interior-mutability async Two mutex types side by side. Mutex (imported from tokio) guards state the pool locks around awaits; std::sync::Mutex guards state that is only touched in synchronous code, like lingering and tor_reserve, and the comment on tor_reserve fixes its lock order. Flags are atomics, and immutable configuration is plain data.
  • smart-pointers backoff and blacklist are Arc<Mutex<…>> because they are shared with PoolMemory, which survives an idle pause. On resume, start keeps only wrong-chain windows: the others are measured on a monotonic clock that stands still while a phone sleeps, so an overnight pause would hand back windows that never ran down.
  • smart-pointers lingering: Vec<([u8; 64], std::sync::Weak<ManagedPeer>)> tracks evicted peers whose sessions may still be open (a read may still hold the Arc). A Weak observes without keeping the peer alive; weak.upgrade() in sweep_lingering answers whether it still exists.

async domain The Gloas resolver needs no trust in the peer: it asks up to four peers for the header by hash, with a 5 s timeout each, and hands every answer to anchor.resolve_header, which recomputes the keccak. domain The served-header backfill uses the same trust rule as the read ladder. A batch enters the eth/69 window only if its numbers are exact, its parent hashes chain, and its top hash equals either the beacon-anchored head hash or the parent hash of the held header just above it. The head probe reuses this gate with a batch of one: a peer that returns the anchored header proves it holds the head, even on eth/68, which announces no number.

Shutdown

An Arc cycle, and how it is broken

The loops each own an Arc<PoolInner>, and PoolInner owns the Tasks that own those loops' handles (tasks.rs). While the loops run, the reference count can never reach zero, so Tasks' own Drop would never fire. Drop for PeerPool, the outer handle, breaks the cycle by aborting the tasks. Without it, dropping the pool would leave its loops running forever. stop() holds the tokio peers guard across peer.close().await, which is legal for an async mutex and would not be for a std one. Drop cannot .await, so it uses try_lock() and skips a locked set rather than block in a destructor.

The pure half of eth_getProof (EIP-1186): which state root a request may be proven at, and the answer types. An eth_getProof answer carries no root, so a client checks it against the stateRoot of the block it named. Other reads may answer a near-head number from head state; a proof at the wrong root would be a well-formed answer that fails the client's check, which is indistinguishable from a forgery. So a proof is served only at a root the node holds attested for exactly that block: the optimistic head, one of the last 128 heads that the current head builds on, the finalized block, or a block hash the anchor places.
