The workspace: crates, features and profiles

Before any .rs file, read the manifests. They answer the questions Gradle answers on the JVM side: what gets built, from what, into which kind of artefact, and with which switches. A few lines here explain whole files later.

Cargo in Gradle terms

A package (one Cargo.toml) builds one or more crates: at most one library (src/lib.rs) plus any number of binaries, examples, tests and benches. A workspace is a multi-project build with one shared Cargo.lock and one target/ directory, like a Gradle root project with include(...). Dependencies are declared by name and version (tokio = "=1.52.3") or by path to a sibling crate (myotis-net = { path = "../myotis-net" }). The Gradle build in this repo calls cargo (cargoBuildHost, cargoTest, cargoNdkAndroid, the two canaries), so both worlds meet in the root build.gradle.kts.

A feature is a named compile-time switch. It has no Gradle twin. The closest picture is a set of Java source folders that exist only when a flag is set. In code, #[cfg(feature = "x")] on an item removes that item entirely when the feature is off: the compiler never type-checks it. A feature can also turn on an optional dependency ("dep:jni") or a feature of another crate ("myotis-net/tor"). Features are additive: if any crate in the build turns a feature on, it is on for everyone who depends on that crate.

The workspace root. It lists the ten member crates, excludes the two standalone ones, pins one release version and one minimum compiler for all members, and owns the release profile. The long header comment (lines 1–41) describes the crates in one paragraph each; it is the best short description of the architecture in the repo.

  • modules-cargo Resolver 2. resolver = "2" resolves features per target and per dependency kind. A [dev-dependencies] feature cannot leak into the shipped library, and a feature asked for under [target.'cfg(...)'.dependencies] stays on that target. Several manifests below rely on both rules.
  • modules-cargo Members and exclusions. Since the September tour two members joined: myotis-wire, the sans-I/O protocol code split out of myotis-net, and myotis-rpcd, the JSON-RPC daemon. exclude keeps tor-poc and roost out of cargo build --workspace, even though they sit in the same directory tree.
  • modules-cargo Inherited package fields. Each member writes version.workspace = true and rust-version.workspace = true, so all of them are 0.1.20 and need rustc 1.91 or newer. Gradle stays the source of truth for the version: verifyCrateVersions fails check if this line disagrees with the root build.gradle.kts, or if a myotis-* manifest stops inheriting it. The Gradle toolchain probe reads rust-version to decide whether an installed cargo is new enough, and verifyRustVersionFloor fails check when a lock update pulls in a crate that needs a newer compiler.
  • modules-cargo error-handling Profiles belong to the workspace. A member's own [profile.*] is ignored. So panic = "abort" applies to every member: a panic ends the process at once instead of unwinding the stack. The roost manifest calls it the right FFI rule for the engine: a Rust panic must not unwind out through a C or JVM frame (depending on the ABI that is undefined behaviour or an abort anyway), so ending at once is the predictable choice. roost, which wants unwind, must therefore be its own workspace root. lto = true plus codegen-units = 1 trade build time for smaller, faster binaries, which matters on mobile.
  • modules-cargo Why myotis-rpcd is a member. The daemon links the engine in-process. The engine already lives under panic = "abort", so the daemon gains nothing from a separate profile, and it adds only tiny_http and clap to the build.

One crate, two artefact kinds, and two features: one decides whether the JNI glue is compiled at all, the other whether the crate links the standard library.

  • modules-cargo unsafe-ffi cdylib and rlib. A cdylib is a C-compatible dynamic library (.so/.dylib/.dll) that a JVM or Node can dlopen. An rlib is Rust's own library format, used when another crate in the workspace depends on this one. myotis-engine is also built as a staticlib (.a) for iOS, through cargo rustc --crate-type staticlib.
  • modules-cargo Optional dependency plus feature. jni is compiled only when the jni feature is on ("dep:jni"), and turning on jni also turns on std. Both are on by default, so the cdylib the Java engine loads has the shim. std = [] enables no dependency: it exists only so that the code can test cfg(feature = "std").

modules-cargo myotis-consensus opts out of the defaults and forwards its own std feature down:

So a default build of myotis-consensus gets the BLS verify core with std but without JNI. A --no-default-features build of consensus gets the verify core with neither.

The execution-layer primitives crate promises to build without the standard library. The manifest shows how that promise is kept: a std feature that forwards to the dependencies' own std features, dependencies with default-features = false, and a dependency that exists only on bare-metal targets.

  • modules-cargo no_std + alloc. Rust's standard library comes in layers. core has no allocation and no OS. alloc adds Vec, String and Box on top of any allocator. std adds files, threads, sockets and the clock. A crate marked #![no_std] links only the first two, so it can run in firmware. On the JVM there is no equivalent: the class library is always there.
  • modules-cargo Why every dependency says default-features = false. Most crates turn on their own std by default. One dependency with its defaults left on would pull std into the whole graph, so each one is opted out and gets std back only through this crate's std = ["sha3/std"].

modules-cargo A [target.'cfg(...)'.dependencies] table applies only when building for a matching target. Here it does not add a crate; it adds a feature (force-soft) to sha2, which already arrives through k256. Under resolver 2 that feature stays on the bare-metal targets, so every other build keeps the fast SIMD backend.

testing The promise is tested by the no_std canary, a Gradle task wired into check. x86_64-unknown-none ships no std at all, so any leak fails here and nowhere else. It builds myotis-wire too:

A second canary, cargoCheckWasm, runs cargo check for wasm32-unknown-unknown on myotis-consensus, myotis-core and myotis-wire. It proves those crates stayed sans-I/O, because tokio and libp2p do not build for plain wasm32. It needs clang, because blst compiles its C sources for wasm.

The wire protocols without an async runtime (Stop 5). Its features let a host take only the execution-layer half and skip the consensus crate, and with it the blst C library.

  • modules-cargo A weak feature: "myotis-consensus?/std". The ? means "turn on std in myotis-consensus, but only if that optional dependency is already enabled". Without the ?, enabling std would also pull in myotis-consensus, and an execution-layer-only host could no longer leave it out.
  • modules-cargo eth2 gates a whole module. In lib.rs, #[cfg(feature = "eth2")] pub mod eth2; means the module does not exist without the feature. The no_std canary builds with --no-default-features, so it builds neither std nor eth2, and therefore no consensus code.
  • modules-cargo testing A feature for other crates' tests. test-util exposes helpers under #[cfg(any(test, feature = "test-util"))]. cfg(test) is true only when this crate's own tests are compiled, so another crate's tests need the feature. myotis-net asks for it in its [dev-dependencies].
Stale or inaccurate comments

Lines 43–46 say that bare-metal builds must set RUSTFLAGS="--cfg aes_force_soft". rust/.cargo/config.toml now sets that cfg per target, so any cargo invocation inside rust/ gets it without an environment variable. Only an embedder building outside this tree still has to set it.

The I/O crate. Its runtime and networking dependencies are pinned exactly (=), because interop with live peers depends on wire-level behaviour of those versions. RLPx's crypto moved to myotis-wire with the code that uses it. Tor support is optional and chooses its TLS backend per target.

modules-cargo "=1.52.3" means exactly this version. A plain "1.52" would mean "any compatible 1.x at or above 1.52", like a Gradle dynamic version. features = [...] picks which parts of tokio to compile; tokio has almost nothing on by default.

  • modules-cargo One optional dependency, two target tables. arti-client is declared twice, once for every target except Android (native-tls) and once for Android (rustls plus bundled SQLite). Both are optional = true, and the single tor feature enables whichever one the current target has. The comment on lines 68–76 explains why it is not one table plus a feature: tor-rtcompat silently prefers native-tls when both are on.
  • modules-cargo fixture-recorder forwards to another crate's feature (myotis-evm/fixture), so turning it on here compiles test tooling in both crates.
  • modules-cargo testing [dev-dependencies] is Gradle's testImplementation. Here it adds tokio's test-util, which enables #[tokio::test(start_paused = true)]: tests run on a virtual clock that jumps forward instantly whenever every task is waiting.
  • modules-cargo testing A crate that depends on itself. myotis-net = { path = ".", features = ["fixture-recorder"] } under [dev-dependencies] is a known Cargo idiom. It turns on one of the crate's own features for its tests and examples only. The library that the engine links is built without it.
  • modules-cargo [[example]] declares a runnable demo in examples/ (cargo run --example live_sync). Cargo also discovers the other files in examples/ on its own; the table only matters when a target needs settings.

The engine library forwards a feature to its dependency: turning on myotis-engine/tor turns on myotis-net/tor, which pulls in Arti. Only the desktop host library and the Android jniLibs are built that way, and only with -PtorEngine.

Follow the feature

-PtorEngine (Gradle) → cargoBuildHost appends --features myotis-engine/tor (the package/feature form, because a bare --features tor with --workspace would apply to every member), and build-android.sh does the same for cargo ndk → myotis-engine's tor = ["myotis-net/tor"] → myotis-net's tor = ["dep:arti-client", "dep:tor-rtcompat", "dep:rustls"] → the compiler now sees #[cfg(feature = "tor")] pub mod tor; in el/mod.rs and the first block of set_tor_enabled in host.rs. Without the feature, those lines do not exist for the compiler, and the function returns false.

macros modules-cargo #[cfg] on a block keeps or deletes that block before type checking. Exactly one of the two blocks survives, and it becomes the function's tail expression. let _ = on; uses the parameter in the Tor-less build so the compiler does not warn about an unused variable.

modules-cargo testing [target.'cfg(unix)'.dependencies] adds libc only on Unix-like targets. The dev-dependency on myotis-evm with features = ["fixture"] is how the engine's own tests reach the EVM's in-memory oracle, while the shipped library is built without it.

revm is pinned exactly and trimmed with default-features = false, which drops its C-based precompile backends in favour of pure-Rust ones. The optional_* features expose switches an eth_call needs (no balance check, no base fee, and so on). The fixture feature lets downstream tests use an in-memory oracle and recorded-world files without shipping them in the engine binary.

modules-cargo testing In code this becomes #[cfg(any(test, feature = "fixture"))] on pub mod fixture; and on FixtureSnapStateOracle: compiled for the crate's own tests, or when a dependent crate asks for features = ["fixture"]. serde_json appears twice: once optional (pulled in only by fixture) and once as a dev-dependency for the crate's own tests.

The Node addon is a cdylib only (Stop 18). It links myotis-engine as a Rust library for its C-ABI symbols and adds napi-rs. [build-dependencies] are used by build.rs, a small program cargo compiles and runs before building the crate.

The JSON-RPC daemon (Stop 19). It has no [lib] table and no [[bin]] table: a package with src/main.rs is a binary by convention. Its dependency list is short on purpose.

  • modules-cargo concurrency No async stack. The engine owns its tokio runtime, and every engine read blocks. So the daemon uses a blocking HTTP server (tiny_http) with a fixed pool of worker threads, like a classic servlet container, and does not depend on tokio itself.
  • modules-cargo cli Trimming features to trim the lock file. clap is already in the lock through uniffi. Turning its defaults off and listing only the needed features avoids the color feature, which would add six crates.

An empty [workspace] table makes this package its own workspace root, with its own Cargo.lock and its own profile. That is the whole trick behind "excluded". It still depends on myotis-net and myotis-consensus by path, so a dependency change in rust/ must update this lock file too.

modules-cargo cli error-handling [[bin]] declares an executable target. With panic = "unwind", a panic unwinds only the tokio task it happens in, and the task's JoinHandle reports it as an error value (JoinError::is_panic()) instead of the process dying on the spot. Be precise about what that buys. The manifest header (lines 15–16) says a malformed chunk "kills one connection", but roost's README corrects this: requests are answered inline on the single libp2p swarm task, so a panic there ends every connection. serve notices the dead task, logs it and exits non-zero, and systemd restarts the daemon (Stop 20). The gain is a controlled, observable restart, not per-connection isolation.

The Tor proof of concept (Stop 21) uses the same empty-[workspace] trick, for a different reason: it always links Arti, and the Arti tree must never burden the engine build or CI. Unlike myotis-net, it pins only native-tls, because it runs on desktop only.

modules-cargo Both standalone crates are pinned at 0.0.0. They are not release artefacts, and verifyCrateVersions only checks manifests that match myotis-*/Cargo.toml.

The smallest crate in the repo: a binary whose three-line main calls uniffi::uniffi_bindgen_main() (Stop 17). It exists so that the generator version always matches the uniffi version the engine links against. It sets its own version instead of inheriting the workspace one, because it is a pinned tool, not a release artefact.

Worth remembering

UniFFI embeds a checksum per exported function in the scaffolding, and the generated Kotlin verifies it at load time. Any change to ffi.rs, even a doc comment, changes a checksum, so the committed bindings must be regenerated afterwards. Regenerate them through Gradle's uniffiGenerateKotlin, not a direct cargo run: the Gradle task also masks the generated checksum comparisons to 16 bits, and the APK workflow's drift check fails on unmasked bindings.

Per-target compiler flags, applied to every cargo invocation inside rust/. The first three tables serve Android: Android 15+ devices can use 16 KB memory pages, and a library linked with 4 KB-aligned segments fails to dlopen there. The last three serve the bare-metal targets of the no_std promise.

modules-cargo -C link-arg=... passes a flag through to the linker. --cfg aes_force_soft defines a custom configuration flag for the compiler, which the aes crate tests with #[cfg(aes_force_soft)]. The aes crate has no Cargo feature for this, so a cfg flag is the only switch. Putting it here rather than in a CI RUSTFLAGS variable means the no_std canary, an embedder building in-tree and a developer at the shell all get the same flags.

Tells rustup which compiler to use inside rust/: the current stable. The minimum version is rust-version in the workspace manifest, enforced by the Gradle probe, rather than an exact pin here, because Rust is optional for most developers and an exact pin would force downloads. The file applies only under rust/; cargo run from the repo root uses rustup's default toolchain.

The rest of rust/

  • Cargo.lock: exact resolved versions of every transitive dependency. Committed, because this workspace produces shipped binaries. roost/ and tor-poc/ each have their own.
  • include/myotis_engine.h: the hand-written C header for capi.rs. A unit test pins its MYOTIS_ABI_VERSION (55 at this snapshot) to lib.rs's ABI_VERSION (Stop 16).
  • build-android.sh / build-xcframework.sh: cross-compilation helpers (cargo-ndk for the Android ABIs, with MYOTIS_TOR_ENGINE adding the tor feature; device and simulator slices packed into an xcframework for Swift hosts).
  • bench/sync_bench.sh: the Rust-vs-JVM cold-sync benchmark (wall time, RSS, CPU).
  • testdata/: conformance corpora generated from the Java engine (el/, lc/), recorded EVM worlds (evm/), a golden snapshot, anchor fixtures and the network catalog. Both engines replay the same bytes (Stop 15).
