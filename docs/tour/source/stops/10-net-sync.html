myotis-net, part 2: the light-client sync loop

sync.rs conducts the consensus side. It defines each chain, starts the libp2p host and one long-lived task that bootstraps from the trusted checkpoint (or resumes a snapshot), walks the sync committee up to the present, then polls finality once per slot. It refuses to start from an anchor older than the weak-subjectivity bound. A new neighbour, cl_fork_watch.rs, listens to what consensus peers advertise and raises an "update required" advisory when the network has moved to a fork this build does not know. The five example binaries reuse these parts as operator tools.

How the pieces run

SyncHandle::start creates four kinds of concurrent work. The swarm task (started by reqresp::start_host_with, Stop 9) owns the libp2p Swarm; everyone else talks to it through a cloneable ReqRespClient, which is just an mpsc::Sender<Command> plus a few shared maps, with a oneshot reply per request. The discovery task owns Discv5 and pushes fork-matched peers into an mpsc channel. The run_sync task owns every piece of sync state. And the request futures that run_sync creates are not tasks at all: they are futures polled by run_sync itself.

State that more than one of them must see lives behind an Arc: the Status the host serves to peers (Arc<LocalStatus>, a std::sync::Mutex), the CL→EL bridge (Arc<ExecAnchor>), the weak-subjectivity knobs (Arc<WsPolicy>, two atomics), the hunt boost (Arc<AtomicBool>), the discv5 table size (Arc<AtomicUsize>), the byte counters (Arc<TrafficMeter>), and now the fork watch (Arc<ClForkWatch>). Everything else is owned by exactly one task.

The consensus-layer light-client driver. It defines each supported chain (ChainConfig: trust anchor, fork schedule, pinned LC servers, discv5 bootnodes, weak-subjectivity bound), now four of them with Chiado. SyncHandle::start launches the host and one long-lived run_sync task. That task bootstraps or resumes, walks the committee with light_client_updates_by_range, polls light_client_finality_update once per slot at a jittered point just past a third of the slot, publishes a SyncStatus, keeps the Status served to peers honest, and feeds the CL→EL ExecAnchor. It does not call the fork watch itself; it only threads the Arc<ClForkWatch> from its config into the host and discovery.

  • interior-mutability AtomicU64 and AtomicBool are mutated through &self, with no mut and no lock: Java's volatile plus AtomicLong. #[derive(Default)] works because both atomics implement Default (zero and false). Relaxed ordering is enough: each flag is read on its own, and nothing else has to become visible together with it.
  • domain saturating_sub in ws_anchor_stale makes a wall clock behind the anchor read as fresh, not as a huge unsigned age. The comparison is >: an age equal to the bound is still fresh.

The finality-poll schedule

domain New since September. The old loop slept one fixed slot after each round, so its poll drifted through the slot. Now each process draws one point per run (a third of the slot, plus a 500 ms margin, plus random jitter of up to a quarter slot, capped at two thirds; finality_poll_offset_ms, fed by getrandom) and sleeps until that point in the next slot. A third of the way in is the attestation and sync-message deadline: the sync aggregate that attests the previous block is out by then, and servers rebuild their latest update as they import it. delay_to_next_poll is pure: it takes "now" as a parameter instead of reading the clock, so the tests can drive it with any time. The clamp in poll_slot_ms plus the saturating operations keep every sum in range for any input. On 12 s slots it also waits at least 11 s after the previous poll started, because Lighthouse serves each light-client protocol once per 10 s per peer.

Gotcha

Dropping a SyncHandle without calling stop() stops nothing. SyncHandle has no Drop impl, and a dropped JoinHandle merely detaches its task. run_sync has no exit path at all; abort() is the shutdown signal. That is why the engine host always calls sync.stop().await.

The weak-subjectivity gate

A light client trusts sync-committee signatures. Validators can leave, though, and once enough members of an old committee have exited, they can sign a forged chain at no cost to themselves. Their signatures would still verify against the old committee. So a light client must not walk forward from an anchor older than the network's weak-subjectivity bound. Here the bound is counted in sync-committee periods (8192 slots: about 27 hours on mainnet, about 11 hours on Gnosis).

  • domain interior-mutability Entry gate. The anchor is the newer of the embedded checkpoint and the persisted snapshot. When it is past the bound, the loop parks in StaleAnchor and re-checks once per second, until the host raises the bound (effective_ws_bound_periods reads the override atomic), gives consent (accept_stale_anchor.load(Relaxed)), or aborts the task. Consent is per run and never persisted. While parked it still keeps the served Status's fork digest in step with the schedule.
  • async tokio::time::sleep(…).await yields the worker thread, so a parked loop costs nothing. It is also a cancellation point: abort() takes effect at the next .await.
  • domain publish_stale_anchor sends a status built from SyncStatus::initial() with only state, period (the refused anchor's) and ws_bound_periods filled in, and tells the ExecAnchor that its finality is no longer current.

ownership Note the two uses of persisted_snap. The gate above only looked at it: persisted_snap.as_ref().map(|s| s.current_sync_committee_period) turns &Option<Snapshot> into Option<&Snapshot> and copies one u64 out. Here if let Some(snap) = persisted_snap moves the snapshot out of the Option, and processor.store.restore(snap) moves it again into the store. After this block persisted_snap is gone; the compiler would reject any later use. A restored store starts on probation (ResumeGuard::resumed()) until an update verifies against it.

domain borrowing The gate runs in two more places. Before a re-bootstrap (lines 2434–2448: reachable when a poisoned snapshot was discarded, so the older checkpoint becomes the anchor again), and here, while running: a committee held in memory ages exactly like a snapshot on disk, so a node that was peer-starved for longer than the bound must not walk forward when peers return. Both of these park in 5 s steps. status_tx.borrow().state reads the value the loop itself last sent, so the warning is logged only when the state changes.

borrowing catch_up(&config, &client, &mut pool, &mut processor, …) lends all the task-owned state at once, twelve arguments. Because this task owns it, the helpers can take &mut with no synchronization, and each borrow ends when the call returns. let _ = std::fs::remove_file(path); ignores the result deliberately. There is no optimistic-update poll: the optimistic head comes from each finality update's attested header.

Verification before trust: bootstrap

  • async ownership One async move block per candidate, each owning its own client clone, wire bytes, peer id and dial addresses. futures::future::join_all(futures).await waits for every reply. Then the first valid one, in candidate order, wins.
  • borrowing iterators-closures let fail = |pool: &mut PeerPool, buf: &mut Vec<String>, id| … takes the pool as a parameter instead of capturing it. A captured &mut pool would stay borrowed for as long as the closure lives, and later code (pool.mark_proven(peer)) could not touch the pool. The closure does capture peers, but only by shared reference, which does not conflict with anything below.

domain error-handling "The peer chose the payload, WE chose the root." The bootstrap header must hash to the embedded checkpoint root. Then processor.verify_bootstrap (new since September; the branches used to be checked inline here) checks that the shape matches the header's fork, that the current sync committee is in the header's state, and that the execution branch binds the execution data to the body, each at the generalized index of the header's fork, so Gloas is covered. It returns Result<(), BootstrapReject>; if let Err(reason) = … handles only the failure. Only after all of that does the peer earn credit (mark_proven, note_served). Credit always follows verification, never mere delivery.

The catch-up pipeline

  • async smart-pointers lifetimes FuturesUnordered<BoxFuture<'static, Answer>> is a set of futures that yields each result as soon as it finishes. BoxFuture is Pin<Box<dyn Future<Output = Answer> + Send + 'static>>: a heap-allocated future whose concrete type is erased, so the set's element type can be written down in the declaration, long before the first push. 'static forces each future to own its client clone, peer and wire bytes; it may not borrow the pool. The pin gives the future a fixed heap address, which an async state machine that may borrow from itself needs once it has been polled.
  • async tokio::select! races "next answer" against "the earliest per-peer quota refill". If the timer wins, the next() future is dropped, but the requests stay inside in_flight, so nothing is lost; continue goes back to the top-up. let Some(…) = next else { continue }; destructures the 5-tuple answer.
  • domain The pipeline keeps at most 32 asks outstanding, at most 4 of them batch asks of up to 128 periods. Lighthouse-class peers (one update per 10 s each) each get a different look-ahead period, while the prefix period is asked at least twice. Out-of-order answers are staged with up to 3 alternates per period, and the pipeline backs off 5→10→20→25 s after idle waves. A peer whose multi-period answer applies two or more periods is promoted to "batch server" and leads selection afterwards.

The comment on in_flight (lines 3150–3151) says it is "Boxed because each top-up's async block is its own anonymous type." That is not quite how the type system works. Each async block in the source has its own type, but every future one source location creates, however many loop iterations run it, has that same type. catch_up has a single push site (line 3375), so an inferred FuturesUnordered<_> would compile, as it does in poll_finality.   • domain The round-scoped failure buffer is a lesson from a real device: striking all 15 speculative losers every slot emptied the peer cache of every proven server (peers=209, catch_up_servers=0). Now the shared cache strikes them only when nothing verified at all.

Publishing and the SYNCED gate

enums-patterns domain update_exec_anchor is the CL→EL trust bridge. A match guard (Payload(e) if e.block_hash != [0u8; 32]) tests the variant and a condition at once; a zero block hash (pre-Merge or absent) falls through to _ => {}. e is a &Box<ExecutionPayloadHeader>, and e.block_hash auto-dereferences through both. Some domain first. Each consensus client advertises an eth2 field in its discv5 ENR: the 4-byte fork digest of its current fork (a truncated hash of the fork version, the genesis validators root and, since Fulu, the blob parameters), the version of the next fork it knows about, and that fork's activation epoch (or FAR_FUTURE_EPOCH for none). A Status message carries only the digest. From that, the watch collects two kinds of evidence. Announced: a peer on one of our digests names a next-fork epoch our schedule does not know. Placed: a peer on a digest we do not know, whose advertised version reproduces that digest under our genesis root and is newer than ours, so it is on a later fork of this chain. A bare digest (a Status) can also be placed against a version some other source announced.

Interior mutability and a scoped lock

  • interior-mutability concurrency Every method takes &self, because the watch is shared behind an Arc by three tasks and the host. The mutable part sits in inner: Mutex<Inner>; the configuration fields beside it are never written after new, so they need no lock. This is the Rust shape of a Java class whose mutable fields are all guarded by one synchronized lock.
  • concurrency borrowing The lock is held only inside the inner block. let Ok(mut inner) = self.inner.lock() else { return; }; takes the guard. It is dropped at the block's closing brace, before the match current that logs. Logging under the lock would make every other observer wait for the log sink. A poisoned lock (a panic while it was held) silently skips the update; evaluate returns None in that case through .ok()?.
  • iterators-closures traits-generics mutation: impl FnOnce(&mut Inner) lets observe_enr_at and observe_status_at pass in their own change as a closure, which is called exactly once. mutation(&mut inner) passes a &mut MutexGuard<Inner>, which deref coercion turns into the &mut Inner the closure expects.
  • ownership inner.last_logged = current; followed by returning current would be a use after move for most types. It compiles because Advisory derives Copy, and so Option<Advisory> is Copy too.

The vote

lifetimes borrowing iterators-closures retain needs &mut access to the maps, so it runs first. After that the function only reads. votes: BTreeMap<&str, Vote> borrows its keys from the Strings in inner.enr_by_source and inner.status_by_source: no string is copied, and the compiler ensures votes does not outlive inner. Calling retain again while votes is alive would not compile. The closure newer_self_consistent captures self and current_version by reference. BTreeMap rather than HashMap gives a fixed iteration order, so a tie resolves the same way on every evaluation and in both engines.

  • traits-generics rank returns a tuple. Tuples implement Ord lexicographically when every element does, false < true for bool, and std::cmp::Reverse flips one element's order. One > therefore encodes the whole tie-break list from the comment: more support, then more placed peers, a known epoch, the earliest epoch, and the lowest version.
  • domain An advisory needs at least MIN_PEERS (3) sources behind one fork and more of them than sources on our chain that announce nothing unknown. It is Active once its activation time has passed or three sources were placed on it, else Scheduled. best.is_none_or(…) (a recent Option method) reads "no best yet, or this one ranks higher".

enums-patterns merge_advisories matches a tuple of two options. (None, cl) => cl binds the second element whatever it is, so the first two arms cover every case where at least one side is None; only (Some, Some) reaches the ranking. The ranking reuses the tuple trick: active beats scheduled, a known time beats an unknown one, then more peers, and on a full tie the EL advisory wins.
