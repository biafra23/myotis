The short answer

UniFFI is a code generator for both sides of a C interface. You write ordinary Rust functions and mark them #[uniffi::export]. At compile time the macro writes, for each one, a C-callable wrapper, a byte-encoded description of its signature (the metadata) and a checksum of that description, all as exported symbols of the compiled library. A separate tool, uniffi-bindgen, reads the metadata out of the compiled .so or .dylib and writes a Kotlin file: JNA declarations for the C functions, converters for each type, and one idiomatic Kotlin function per export. At run time the Kotlin side loads the library through JNA, compares every checksum with the value it was generated from, and then calls through.

So two generated halves must agree byte for byte. The Rust half is regenerated on every cargo build; the Kotlin half only when someone runs ./gradlew uniffiGenerateKotlin. The checksums catch the moment they stop agreeing.

In Myotis the exported surface is deliberately simple. The 55 functions in ffi.rs take and return only i32, i64, bool, String and Option<String> (or return nothing). Anything compound (an account proof, a block, a status) is a JSON string. That keeps UniFFI's job small and makes its machinery easy to see.

2. What the macros write

Rust macros run inside the compiler and emit ordinary Rust code. setup_scaffolding! is a function-like macro invoked once. #[uniffi::export] is an attribute macro: it receives the function's source as tokens and returns the function plus new items next to it. Both live in the uniffi_macros crate, a proc-macro crate: a compiler plugin written in Rust, compiled for the build machine and run by rustc.

  • macros #[proc_macro] and #[proc_macro_attribute] mark the entry points. Each receives a TokenStream (the tokens inside the parentheses, or the item under the attribute) and returns a new one. syn parses tokens into a syntax tree; quote! turns a template back into tokens.
  • error-handling macros Errors become compile_error! invocations (into_compile_error), so a misuse shows up as an ordinary compiler error at your code, not as a crash of the macro.
  • macros do_export keeps your function (altered_input) and appends the generated items (output). For a free function, expand_export (export.rs, lines 45–50) dispatches to gen_fn_scaffolding, shown below.

The crate-wide glue

  • macros quote! { … } builds the output tokens, and #name splices in a value, like a template engine for Rust code. format_ident! builds identifiers such as ffi_myotis_engine_uniffi_contract_version. #UNIFFI_CONTRACT_VERSION becomes the literal 30, a constant in uniffi_meta 0.32 that identifies the FFI conventions of this UniFFI release.
  • unsafe-ffi #[unsafe(no_mangle)] keeps the symbol name exactly as written instead of Rust's mangled form, so C (and JNA) can find it by name. It is spelled unsafe(…) because two crates exporting the same unmangled name would silently collide at link time. extern "C" selects the C calling convention.
  • traits-generics pub struct UniFfiTag; is a unit struct: a type with no fields and no size. It exists only to be named as a type parameter, explained below.

unsafe-ffi ownership The four per-crate buffer functions: ffi_myotis_engine_rustbuffer_alloc, _from_bytes, _free and _reserve. Each is a two-line forwarder to uniffi_core (section 3). Each library gets its own copies, with the crate name in the symbol, because each cdylib carries its own allocator: a buffer must go back to the library that made it. Notice that _alloc is a safe extern "C" fn, while the three that receive a buffer or foreign bytes are unsafe extern "C" fn: they rely on the caller's promise that the buffer came from this library. The same macro emits rust_future_* functions (line 108) for async exports, which Myotis does not use, and a re-export hack for builds that combine several UniFFI crates in one library.

Why a tag type: the orphan rule

Rust lets you write impl Trait for Type only if your crate defines the trait or the type. Otherwise two crates could provide conflicting impls. UniFFI wants every consumer crate to be able to implement its conversion traits, even for types from third crates. The trick: the traits take a type parameter, FfiConverter<UT>, and the generated code always uses FfiConverter<crate::UniFfiTag>. Because UniFfiTag is local to myotis_engine, an impl mentioning it is allowed there. For built-in types, uniffi_core writes blanket impls such as unsafe impl<UT> FfiConverter<UT> for String, which apply to every tag. Java has no orphan rule, because Java has no impls outside a class; the nearest analogy is a type-class instance.

3. The wire vocabulary: RustBuffer and the converter traits

RustBuffer

  • unsafe-ffi The rules, in the type's own doc comment. A RustBuffer is only ever made from a Vec<u8>; it has no Drop; it must come back to Rust to be destroyed; the foreign side may only write bytes up to capacity and adjust len; and the foreign side must never wrap its own memory in one (that is what ForeignBytes is for).
  • unsafe-ffi #[repr(C)] fixes the layout. Without it, Rust may reorder struct fields. With it, the layout is exactly a C struct { uint64_t capacity; uint64_t len; uint8_t *data; }, which is what the Kotlin RustBuffer declares field by field (section 6). The fields are pub(crate), so no other crate can build an invalid one.
  • concurrency unsafe-ffi unsafe impl Send for RustBuffer {} (line 67): a struct holding a raw pointer is not Send by default, because the compiler cannot know who else uses the pointer. UniFFI asserts it is safe to move between threads, which async futures need.

ownership smart-pointers unsafe-ffi Giving up ownership. new_with_size allocates a zero-filled Vec of the requested length; this is what Kotlin's alloc gets. from_vec records the three parts. ManuallyDrop::new(v) wraps the vector so that its destructor will not run when v goes out of scope. Without it, the Vec would free its buffer at the closing brace and the returned RustBuffer would point to freed memory. The try_from(…).expect(…) calls can only panic on a platform whose usize is wider than 64 bits.

ownership smart-pointers unsafe-ffi Taking ownership back. destroy_into_vec(self) consumes the buffer and rebuilds an owning Vec with Vec::from_raw_parts(data, len, capacity), which then frees normally when dropped. It is the only place a buffer's memory is reclaimed. The checks are defensive: a null pointer is accepted only with zero length and capacity (a foreign side may send an empty buffer that way), and len <= capacity is asserted. destroy is drop(self.destroy_into_vec()). In Java terms, from_vec detaches an off-heap buffer from its cleaner, and destroy_into_vec re-attaches it.

unsafe-ffi error-handling The runtime behind the four per-crate functions of section 2. Each wraps its work in rust_call, so even buffer management reports failures through a call status. uniffi_rustbuffer_from_bytes copies foreign memory into a new Rust buffer (as_slice().to_vec()); the Kotlin bindings declare it but do not use it.

The conversion traits

traits-generics The module doc draws the family tree. FfiConverter is the general trait you implement; the generated code uses only the narrower ones: Lift for arguments coming in, Lower for values going out, LowerReturn for return values (which lets Result and () be handled specially), LiftReturn/LowerError for callbacks and errors, and TypeId for the metadata. derive_ffi_traits! generates the narrow impls from the general one.

  • traits-generics An associated type plus five items. type FfiType is the C-compatible type (a number, or RustBuffer). lower goes Rust → foreign; try_lift goes foreign → Rust and returns a Result because the foreign side might send something invalid. write and try_read serialize a value into a byte buffer when it is nested inside something else, such as the String inside an Option<String>. TYPE_ID_META is the type's code in the metadata.
  • ownership borrowing lower(obj: Self) takes the value by value: lowering may hand ownership to the foreign side, so the Rust value must be consumed. try_read(buf: &mut &[u8]) is a mutable reference to a slice: the reader moves the slice's start forward after each item without touching the bytes, like a cursor.
  • traits-generics unsafe-ffi The trait is pub unsafe trait. An unsafe trait means implementing it is a promise the compiler cannot check, here that the impl matches what the generated foreign code does. FfiType: FfiDefault is a bound: every FFI type must have a placeholder value to return when a call fails (see ffidefault.rs in the deep dive below).
  • traits-generics Default methods. Lift::try_lift_from_rust_buffer and Lower::lower_into_rust_buffer have bodies in the trait, like Java default methods. They are how compound values travel: write everything into a fresh Vec, hand it out as a RustBuffer; on the way in, rebuild the Vec, read one value, and refuse leftover bytes (bail! from anyhow returns an error early).
  • error-handling LowerReturn returns Result<Self::ReturnType, RustCallError>. For a plain type it is always Ok. For a Result<T, E> return type, its impl turns Err(e) into RustCallError::Error(buffer), which becomes status code 1 and a typed Kotlin exception. Myotis has no such export. handle_failed_lift has a default body: every failed lift becomes an internal error with a message.

macros traits-generics A macro_rules! macro deriving trait impls. This is the other kind of Rust macro: pattern-matching on tokens, with no compiler plugin. derive_ffi_traits!(blanket String) (in ffi_converter_impls.rs, line 450) expands to eight unsafe impl<UT> … for String blocks, each delegating to FfiConverter. The LowerReturn arm shows the plain case: ReturnType is the Lower type, and lower_return wraps lower in Ok. $crate refers to uniffi_core wherever the macro is used.

The impls Myotis uses

macros bytes-strings Numbers are their own FFI type. One macro_rules! template stamps out the impl for all ten numeric types. lower and try_lift are the identity: an i64 travels as an i64. write and try_read go through the bytes crate's put_i64/get_i64, which are big-endian. check_remaining turns a short buffer into an error instead of a panic.

bytes-strings error-handling bool crosses as i8 "to avoid problems with handling C-compatible boolean values on JVM-based languages". Lifting is strict: anything other than 0 or 1 is an error. The Kotlin side is lenient in the other direction (section 6).

  • bytes-strings ownership Zero-copy in both directions. A Rust String is a Vec<u8> that is guaranteed to hold UTF-8. obj.into_bytes() converts it into that vector without copying, and from_vec hands it out. On the way in, destroy_into_vec rebuilds the vector and String::from_utf8_unchecked relabels it as a String, again without copying. At the top level the buffer's own len is the string length, so no length prefix is written.
  • unsafe-ffi bytes-strings from_utf8_unchecked trusts Kotlin. Rust's safe code assumes every String is valid UTF-8; an invalid one is undefined behavior. This lift does not check. It is sound only because the generated Kotlin encodes strings with an encoder that refuses malformed input (section 6). That refusal is why RustEngineNative sanitizes strings first (section 7).
  • bytes-strings Nested strings are different. write puts a big-endian i32 length in front of the bytes, and try_read copies the bytes out (to_vec) and validates them with String::from_utf8. The comment on write admits the unwrap could panic for a string over 2 GiB.

enums-patterns bytes-strings Option<T> cannot be one pointer, so it is always serialized into a RustBuffer: one tag byte (0 = None, 1 = Some), then T's own write format. For holder: Option<String> that is tag, big-endian i32 length, UTF-8 bytes. impl<UT, T: Lower<UT>> Lower<UT> for Option<T> reads "for any T that can be lowered, Option<T> can be lowered too": a generic impl with a trait bound, resolved at compile time. Any tag byte other than 0 or 1 is an error.

Deeper: FfiDefault and ForeignBytes

traits-generics error-handling A C function must return something even when it failed. FfiDefault names that placeholder: 0, false, (), a null pointer, or an empty RustBuffer with a null data pointer (which destroy_into_vec accepts as empty). The foreign side ignores it because the status says the call failed.

ForeignBytes (ffi/foreignbytes.rs, lines 25–32) is the opposite of RustBuffer: a read-only view of memory the foreign side owns, valid only for the duration of one call, with an i32 length "for compatibility with JNA". The generated Kotlin declares it, and its comment there says it is not used, because copying into a RustBuffer is just as cheap from the JVM.

4. Errors and panics

  • unsafe-ffi error-handling An out-parameter instead of exceptions. C has no exceptions, so every scaffolding function takes a pointer to this struct. The caller initializes code to 0 (success) with an empty buffer. Rust overwrites it only when something went wrong.
  • ownership The comment spells out the ownership: error_buf belongs to the foreign side. Rust never frees what it was given and sets it at most once, so the empty buffer it replaces cannot leak. ManuallyDrop here documents that this field is never dropped by Rust.

enums-patterns error-handling #[repr(i8)] gives the enum a fixed one-byte representation with the listed values: 0 success, 1 a returned Err, 2 an unexpected error, 3 cancelled (async only). TryFrom<i8> converts back, returning the unknown byte as the error. RustCallError is what the generated closure produces on failure: Error(RustBuffer) for a serialized Err value, InternalError(String) for everything else, such as the LiftArgsError message "Failed to convert arg '…'".

traits-generics iterators-closures rust_call is what every scaffolding function calls. The bounds say: the callback runs once (FnOnce), may be unwound through (UnwindSafe, a marker that the closure leaves no broken shared state behind if it panics), and returns either the value or a RustCallError. On failure it returns R::ffi_default().

  • error-handling enums-patterns catch_unwind runs the closure and returns Err(payload) if it panics, like a try { } catch (Throwable t) around the call. The nested patterns Ok(Ok(v)), Ok(Err(…)) and Err(cause) separate "returned normally", "returned an error" and "panicked".
  • smart-pointers error-handling A panic payload is a Box<dyn Any + Send>: a value of unknown type. downcast_ref::<&'static str>() and downcast_ref::<String>() try the two types panic! usually produces, like an instanceof check. The message is lowered inside a second catch_unwind (with AssertUnwindSafe, a wrapper that overrides the UnwindSafe check), so even a panic while formatting cannot escape across the C boundary.

error-handling modules-cargo But in Myotis the catch never happens. With panic = "abort" a panic does not unwind at all: the process is aborted on the spot, and catch_unwind has nothing to catch. This profile applies to every --release build of the workspace, which is how cargoBuildHost and rust/build-android.sh build the library the hosts load. Only an unwinding build (the default dev profile, for example a plain cargo test) would turn a panic into status code 2 and a Kotlin InternalException. That is why the ffi.rs module doc insists on "panic-free by construction": every failure in host.rs is returned as a sentinel or an {"error": …} JSON string, and none of the 55 exports returns a Result, so code 1 never occurs either.

Two kinds of failure, two channels

For Myotis, the UniFFI status channel is a safety net for bugs. Ordinary failures travel inside the JSON: {"error": "…"} for "could not answer" (Java raises EngineException), and a complete result with failReason set for "answered, but could not verify". UniFFI could map a Rust Result<String, MyError> to a typed Kotlin exception (code 1); the engine does not use that.

5. Build time: from the compiled library to Kotlin

The smallest crate in the workspace: a binary whose main runs UniFFI's bindings generator. It exists so that the generator always comes from the same uniffi version as the scaffolding the engine is compiled with: both are workspace members and resolve uniffi 0.32 through the one rust/Cargo.lock. Library mode: reading the metadata back out of the binary

unsafe-ffi bytes-strings enums-patterns --library selects UniFFI's library mode. extract.rs parses the compiled file with the goblin crate; the match on Object::parse covers ELF (Linux, Android), Mach-O (macOS, iOS), PE (Windows), static archives and COFF. It then walks the symbol table and collects every symbol whose name starts with UNIFFI_META (macOS prefixes symbols with _, hence the strip_prefix). The bytes of each static are the metadata buffers from section 2. The generator never parses Rust source: what it sees is what the compiler built, so the two halves cannot disagree at generation time.

bytes-strings uniffi_meta's reader decodes each buffer into a FnMetadata and, at the end of every item, recomputes the checksum over exactly the bytes it consumed. That number is what the generator writes into the Kotlin as the expected value.

traits-generics The checksum hash. 64-bit FNV-1a (start at 0xcbf29ce484222325; for each byte, XOR it in and multiply by 0x100000001b3 with wrapping_mul, which wraps on overflow instead of panicking in debug builds), folded to 16 bits by XOR-ing the four 16-bit quarters. It is a while loop because for loops over iterators are not allowed in a const fn. uniffi_meta/src/metadata.rs has a hand-kept copy of this function for the generator. A 16-bit checksum catches accidental drift, not tampering: each changed function has a 1-in-65,536 chance of going unnoticed.

The Gradle task that runs it, in full

  • modules-cargo dependsOn(cargoBuildHost): the generator needs a fresh cargo build --release of the host library first. hostLibNames.last() is the engine library's file name for this OS. cargo run --release -p uniffi-bindgen builds and runs the three-line binary. --no-format skips running a Kotlin formatter over the output, which is why the generated wrappers have their odd indentation.
  • modules-cargo onlyIf { rustAvailable }: without cargo the task skips, and the committed file stays as it is. That is the reason the file is committed at all: a JVM-only machine compiles the Kotlin without ever running Rust. inputs (the Rust sources and the cargo version) and outputs (the .kt file) let Gradle skip the task when nothing changed.

unsafe-ffi A fix applied after generation. The Rust checksum functions return u16, but UniFFI 0.32's Kotlin template declares them as returning Int (a 32-bit JVM int) and compares the full value. A 16-bit return value only occupies the low half of the return register, and the x86-64 calling conventions do not promise that the upper half is zero. The comment records a debug Linux build returning 0x5DB5166E for checksum 5742 (0x166E), and a Windows build that failed every check and silently fell back to the Java engine. The doLast block rewrites each comparison to (… and 0xFFFF) != N with a regex, then checks that the number of rewritten comparisons equals the number of declared checksum functions and that none is left unmasked, so a future UniFFI with a different output shape fails the task instead of passing half-fixed. The triple-quoted """…""" strings are Kotlin raw strings, so the regex needs no double escaping.

6. The Kotlin side

modules-cargo The generated file is 2,384 lines. Its header explains why all helper code is inline: the helpers must match the exact uniffi version that compiled the Rust side. Most of the file is generic support that Myotis never calls (async futures, callback interfaces, a handle map, Disposable). The parts this API uses are below, roughly in file order, followed by the wrapper functions.

The buffer types

  • unsafe-ffi The same struct, seen from JNA. A JNA Structure subclass describes a C struct; @Structure.FieldOrder fixes the field order to match Rust's #[repr(C)] (capacity, len, data). Unsigned u64 becomes a signed Long because the JVM has no unsigned 64-bit type, as the comment notes. @JvmField makes the Kotlin properties plain Java fields, which is what JNA reads by reflection.
  • unsafe-ffi ByValue versus a plain Structure. The nested ByValue class tells JNA to pass and return the struct by value (copied into registers or the stack), as the Rust signatures expect for RustBuffer. A plain Structure parameter is passed as a pointer, which is how the call status travels.
  • unsafe-ffi ownership alloc and free in the companion object (Kotlin's place for static members) are thin calls to the two Rust functions that setup_scaffolding! generated, each through uniffiRustCall. alloc also refuses a null data pointer. Kotlin never frees native memory itself.
  • bytes-strings asByteBuffer() wraps the native memory in a direct java.nio.ByteBuffer of length len, without copying. Reads and writes through it touch Rust's memory directly. ByteOrder.BIG_ENDIAN matches the bytes crate on the Rust side.

unsafe-ffi ForeignBytes, the Kotlin twin of the Rust struct, with the generator's own comment that it is "not actually used at the moment". Its len is an Int, matching Rust's i32.

The converter interface

  • traits-generics The Kotlin mirror of Rust's FfiConverter. FfiConverter<KotlinType, FfiType> has lift/lower for top-level values and read/write for nested ones, the same split as on the Rust side. One addition: allocationSize, because Kotlin must ask Rust for a buffer of a known size before writing into it. The comment explains the pessimistic estimate for strings (3 bytes per UTF-16 code unit).
  • ownership error-handling lowerIntoRustBuffer asks Rust for allocationSize bytes, writes through a ByteBuffer view, then sets len to the number of bytes actually written with writeField (which also copies the field into the native struct). If writing throws, it frees the buffer before rethrowing. liftFromRustBuffer reads one value, insists that nothing is left over (the twin of Rust's leftover-bytes check), and frees the buffer in finally.
  • traits-generics FfiConverterRustBuffer supplies lift and lower as default methods for every type that travels serialized, such as String?.

The call status and the call helpers

error-handling unsafe-ffi UniffiRustCallStatus mirrors the Rust struct: a Byte code and an embedded RustBuffer.ByValue (a struct inside a struct, not a pointer). The three constants are the Rust enum's values. It is passed as a plain Structure, so JNA gives Rust a pointer to native memory it manages for this object, and Rust's &mut RustCallStatus points there. JNA writes the Java fields into that memory before the call and reads them back after it. InternalException is the one exception type this API can throw.

  • iterators-closures error-handling Turning the status into exceptions. uniffiRustCallWithError creates a fresh status object for every call, runs the native call (passed as a lambda that receives the status), then checks it. inline fun copies the function body into each caller at compile time, so the lambda costs no object allocation, a Kotlin feature with no Java equivalent.
  • error-handling uniffiCheckCallStatus maps 1 to the error handler's exception and 2 to InternalException carrying the lifted message (or "Rust panic" if Rust could not even build one). uniffiRustCall uses UniffiNullRustCallStatusErrorHandler, which frees the buffer and reports "Unexpected CALL_ERROR", since no export returns Result.
  • concurrency The comment at the top ("we usually need to be synchronized to call this safely") is generic. Each call creates its own status object, and nothing here is shared between threads, so concurrent calls from several JVM threads are fine.

Loading, and the integrity gate

unsafe-ffi findLibraryName returns the system property uniffi.component.myotis_engine.libraryOverride if set, otherwise "myotis_engine", which JNA maps to libmyotis_engine.dylib, .so or myotis_engine.dll. RustEngineNative sets the override for a development build (section 7).

  • unsafe-ffi JNA direct mapping. Native.register(Class, name) loads the library and binds every external fun of that class to the native symbol with the same name, eagerly: a missing symbol fails here with UnsatisfiedLinkError, not at the first call. Kotlin's external is Java's native.
  • concurrency A Kotlin object's init runs in the class's static initializer, exactly once, under the JVM's class-initialization lock. If it throws, the JVM wraps the exception in ExceptionInInitializerError, and every later use of the class fails with NoClassDefFoundError. The checks are in an init block, so a mismatch makes the whole integrity class unusable.
  • unsafe-ffi The checksum functions live in their own object, apart from UniffiLib. The generated comment explains the split: one interface with all methods once exceeded a JVM size limit for large crates, and it notes this reasoning predates direct mapping.

unsafe-ffi The declarations JNA binds. Compare with the Rust scaffolding: handle: i64 is Long, each RustBuffer is RustBuffer.ByValue, &mut RustCallStatus is a plain UniffiRustCallStatus, and bool returns are Byte. The buffer functions follow, with u64 sizes as Long. If any of these types disagreed with the Rust side, JNA would pass the wrong bits and nothing would notice except the checksums. The rest of UniffiLib declares the unused rust_future_* functions.

macros domain bindings_contract_version = 30 and the 55 numbers such as 48343 are literals the generator wrote from the metadata it read. The library loaded at run time answers ffi_myotis_engine_uniffi_contract_version() and uniffi_myotis_engine_checksum_func_request_account_json(). If either disagrees, the library was compiled from different source (or a different UniFFI) than the bindings, and the code refuses to continue. Note the and 0xFFFF from the Gradle post-processing, and the unhelpful message "try cleaning and rebuilding your project": in Myotis the fix is usually ./gradlew uniffiGenerateKotlin or a rebuilt library.

unsafe-ffi The checks only run if someone asks. Mentioning an object forces its initialization. A plain call like requestAccountJson touches only UniffiLib, which registers its functions without the checksum checks. So a host must call uniffiEnsureInitialized() before anything else, which is the first thing RustEngineNative does.

The type converters

traits-generics bytes-strings FfiConverterLong is the identity, like Rust's numeric impl, with 8-byte getLong/putLong for nested use. FfiConverterBoolean lowers to 1 or 0, but lifts any non-zero byte as true: more lenient than Rust's lift, which refuses anything but 0 and 1. That is harmless here, since Rust only ever sends 0 or 1.

  • bytes-strings ownership lift, Rust → Kotlin. It copies len bytes out of native memory into a JVM ByteArray, decodes them, and in finally calls RustBuffer.free, a native call back into Rust that rebuilds and drops the Vec. After that line no Rust memory is referenced from Kotlin, and the finally frees the buffer even if decoding throws.
  • bytes-strings ownership lower, Kotlin → Rust. toUtf8 encodes the UTF-16 Kotlin string into UTF-8 with CodingErrorAction.REPORT, so a lone surrogate throws MalformedInputException instead of being replaced. This is what makes Rust's unchecked lift sound. Then RustBuffer.alloc makes a native call into Rust for memory of exactly that size, and put copies the bytes into it. One string argument costs one extra native round trip.
  • bytes-strings Top-level versus nested, as in Rust: lift/lower use the buffer's own length, while read/write use an Int length prefix. The comment at the top says so: FfiConverterString deliberately does not extend FfiConverterRustBuffer.

enums-patterns bytes-strings String? uses the serialized path: FfiConverterRustBuffer's default lower calls lowerIntoRustBuffer, which allocates allocationSize bytes (1 for the tag, plus 4 + 3 per code unit for a string), writes tag 0, or tag 1 and the prefixed string, then sets len. The buffer's capacity is usually larger than its length, which is why RustBuffer carries both: Rust must free the whole capacity.

The public wrapper functions

  • unsafe-ffi Read it inside out. Each argument is lowered (FfiConverterLong.lower returns the Long unchanged; FfiConverterString.lower allocates and fills a RustBuffer). uniffiRustCall { _status -> … } creates a fresh status object and passes it as the last argument. UniffiLib.uniffi_myotis_engine_fn_func_request_account_json is the JNA-bound native function. Its RustBuffer.ByValue result goes to FfiConverterString.lift.
  • modules-cargo A top-level function. Kotlin functions outside a class compile into a JVM class named after the file, here Myotis_engineKt, as static methods. That is why the Java caller writes Myotis_engineKt.requestAccountJson(…). Names are converted from snake_case to camelCase, the backticks around every name protect against Kotlin keywords, and the Rust doc comment became KDoc.

enums-patterns Two variations. getStorageProofJson lowers its String? through FfiConverterOptionalString. stopHandle, whose Rust function returns (), has no lift at all: its body is the uniffiRustCall expression, which returns Unit.

Deeper: two small flaws in the generated code

A leak on a failed lowering. In requestAccountJson, the arguments are lowered left to right inside the call expression. If lowering block throws (a malformed string), the RustBuffer already allocated for address is never passed to Rust and never freed: a small native leak per failed call. As far as I can read the code, nothing in the generated file guards against this. In Myotis it cannot happen through RustEngineNative, which replaces every malformed string with "" before the call (section 7).

A message template. Line 292 builds "Unknown rust call status: $status.code". A Kotlin string template $status ends at the identifier, so this prints the whole status object followed by the literal text .code; ${status.code} was meant. It only matters for a status code Rust never sends.

7. The Java callers

  • domain A static delegator. The class doc summarizes this stop from the Java side: compound values are still JSON, availability means "the bindings initialized and the ABI handshake matched", and every string argument keeps the old hand-JNI null tolerance. EXPECTED_ABI_VERSION is a hand-kept copy of the Rust constant; the trailing comment is its changelog.
  • concurrency private static final boolean AVAILABLE = load(); runs load() once, in the class's static initializer, under the JVM's class-initialization lock: the Java equivalent of a lazily initialized static in Rust.
  • domain Finding the library (lines 51–67). An explicit -Dmyotis.engine.lib path is forwarded to UniFFI's libraryOverride property. Otherwise java.library.path, where the run and test tasks put rust/target/release, is copied into jna.library.path, because JNA only reads the latter.
  • error-handling Three outcomes, all non-fatal. No library on the search path gives UnsatisfiedLinkError, logged at info level: the normal case on a machine without cargo. A library that fails the contract or checksum check arrives as ExceptionInInitializerError, so the code unwraps its cause for the warning. A library that passes but reports a different ABI_VERSION is also refused. In every case isAvailable() returns false, and the :myotis-engines selector serves the Java engine instead (the comment in AbiVersionMirrorTest, section 10, describes this fallback). engineInit() also installs the ring-buffer log subscriber (ffi.rs lines 23–31), so the handshake is the first real call into the engine.

bytes-strings Keeping the generated encoder from throwing. nz() turns null, and any string with an unpaired surrogate (which a JSON-RPC client can send), into "". Without it, FfiConverterString.lower would throw MalformedInputException. The old hand-JNI layer behaved like nz(), and the delegator keeps that behavior. wellFormed is a hand-written scan instead of an encoder probe because it runs on every argument; the comment counts the cost.

enums-patterns The two delegators this stop follows. For the optional holder, a malformed string becomes null rather than "", matching what the old shim did (a decode failure was None). Java's null reaches Kotlin as a String? that is null, which lowers to tag byte 0.

  • concurrency domain gated(…) wakes a paused chain, waits (bounded) while it warms up, and counts the call as in flight so the idle timer cannot pause the chain mid-read. Supplier<T> defers the native call until the gate opens.
  • error-handling domain Where the boundary is type-checked. accountFromJson fills the 23-argument io.myotis.api record AccountProofResult field by field, with defaults for missing keys, and turns a type mismatch into an EngineException. Field names and types are checked here, at run time, in Java, not by any compiler. The // ABI >= 41 and // ABI >= 52 comments mark keys added as payload extensions.

error-handling parseResultOrThrow in two halves: parse with minimal-json (a null, blank or malformed string throws), then turn {"error": …} into EngineException. A verification failure is not an error here: it is a normal result with failReason set.

8. How the library reaches the JVM and Android

JNA has to find a file called libmyotis_engine.* at run time. There are three situations.

  • Development (daemon, desktop app, tests). cargoBuildHost writes the library to rust/target/release/, and RustEngineNative.load() bridges java.library.path to jna.library.path, as shown above.
  • A desktop consumer of the engine library. The jar does not contain the native library; a separate artifact carries it, as the consumer documentation explains:

modules-cargo The natives jar puts <platform>/libmyotis_engine.* on the classpath, where JNA finds it, extracts it to a temporary file and loads it. Note the warning in the middle: a library from another release with the same FFI passes every check, because the checks compare shapes, not versions.

  • Android. The .so files are packed into the AAR and from there into the APK, where the system's dynamic linker finds them by name. In RustEngineNative's words, "On Android JNA resolves the bundled jniLibs on its own."

Building the Android libraries

modules-cargo cargoNdkAndroid runs rust/build-android.sh when the Android toolchain is present and -PskipRustEngine is not set. Its inputs include the cargo, cargo-ndk and NDK versions, so a toolchain change rebuilds. cargo ndk cross-compiles the engine (and the BLS library) with the NDK's linker for two ABIs and writes <abi>/libmyotis_engine.so into myotis-engine/src/androidMain/jniLibs, the layout Android's Gradle plugin expects. Nothing there is committed. The script then deletes any other .so it produced and checks that every library is 16 KB aligned.

modules-cargo The jniLibs directory is a source of the AAR only when the Rust engine is wanted. The comment explains why the gate is on the source rather than a packaging filter: a leftover .so from an earlier build would otherwise ship, fail UniFFI validation on the device, and silently fall back to the Java engine.

JNA's own native half

  • modules-cargo JNA itself needs a native library, libjnidispatch.so, to call anything. The plain JNA jar carries only desktop dispatchers; the Android ones ship in jna-<v>.aar. A detached configuration (isCanBeConsumed = false, not on any classpath) downloads that aar, and extractJnaAndroidNatives copies only jni/<abi>/… into this module's jniLibs, renaming paths to <abi>/….
  • modules-cargo The JNA jar version is pinned with strictly, so the published POM carries the constraint too: JNA refuses to run when its jar and its native dispatcher differ. Sync rather than Copy removes files no longer in the spec, and the doLast check fails the build if an ABI got no dispatcher.

The Android build regenerates the bindings

  • modules-cargo Everything hangs off preBuild, the first task of every Android build path. It always extracts the JNA dispatcher and runs the toolchain gate; unless -PskipRustEngine is set, it also runs uniffiGenerateKotlin, cargoNdkAndroid and verifyAndroidJniLibs. The comment on line 234 explains why the explicit dependsOn(extractJnaAndroidNatives) is needed: a task registered as a source directory does not carry a dependency through the Android plugin.
  • modules-cargo Generated from the host library. uniffiGenerateKotlin depends on cargoBuildHost, so the Android bindings are generated from the macOS or Linux library, not from the Android .so. That works because the metadata comes from the source, which is the same for both targets (ffi.rs has no #[cfg]-gated exports).
  • modules-cargo mustRunAfter orders tasks without adding them: the symbol check must see the fresh .so and the fresh .kt, and both expensive Rust builds wait for the cheap toolchain gate, so a machine without the NDK fails fast.

testing bytes-strings verifyAndroidJniLibs collects, with a regex over the committed Kotlin, every uniffi_myotis_engine_* and ffi_myotis_engine_* name that Native.register will bind, then reads each built .so as ISO-8859-1 text (one char per byte) and checks that every name occurs. It is a build-time version of the eager binding JNA does on the device. As the comment says, it catches a missing symbol, not a changed signature under the same name; that is left to the checksums and to CI's regenerate-and-diff. It also checks that each library starts with the ELF magic bytes.

Desktop builds do not regenerate

modules-cargo A dependsOn here would put a release cargo build in front of every JVM compile and break the rule that Rust is optional for the JVM hosts. mustRunAfter only orders the two tasks when both are in one build. Freshness for everyone is enforced by CI: the comment says the APK workflow regenerates the bindings and fails on any difference.

9. Why compound values cross as JSON

UniFFI can pass structured data. A #[derive(uniffi::Record)] struct becomes a Kotlin data class, serialized into a RustBuffer field by field with write/try_read, exactly as Option<String> is above. The project's design notes describe that typed mapping for the whole io.myotis.api contract, and then explain what was built instead:

The reasons, from the code and these notes:

  • It was a transport swap. The ffi.rs module doc: "TRANSPORT SWAP ONLY: these functions mirror the old hand-JNI natives 1:1". The JSON shapes already existed, Java already parsed them, and golden tests on both sides (rust/testdata/…, RustVerifiedReadJsonTest and others) pinned them. Replacing hand-JNI with UniFFI changed how bytes move, not what they mean.
  • One schema for three routes. The iOS C ABI and the Node addon can only pass char*. Because the UniFFI route also passes JSON, eljson.rs serializes each result once for all hosts, and the same golden files cover them.
  • A small, stable FFI surface. With only integers and strings crossing, a checksum changes only when a function is added or its parameters change. Adding a field to a result is a payload change: no signature changes, no regeneration, and older readers ignore the new key (the ABI_VERSION history in lib.rs records many such "payload extension, no signature change" steps).

The costs are real. A result is serialized to text in Rust, copied across, and parsed again in Java. The compiler no longer checks that both sides agree on a field's name or type; the golden tests and the defensive parsing in RustChainHandle do that instead. And the ABI_VERSION number has to be bumped by hand for every payload change.

11. The iOS route, for contrast

iOS does not use UniFFI. capi.rs exports a hand-written C interface over the same host functions, declared in rust/include/myotis_engine.h. Kotlin/Native reads that header with cinterop and generates Kotlin declarations for it at build time. There is no JNA, no JVM and no RustBuffer: strings are NUL-terminated C strings.

  • unsafe-ffi bytes-strings Incoming: copy and repair. CStr::from_ptr borrows the caller's bytes up to the NUL, to_string_lossy replaces invalid UTF-8 with U+FFFD instead of trusting it, and into_owned copies, so Rust does not depend on how long the caller keeps its buffer. Compare UniFFI's from_utf8_unchecked, which neither copies nor checks.
  • unsafe-ffi ownership Outgoing: the same allocator rule. CString::into_raw gives up ownership exactly like RustBuffer::from_vec. An interior NUL makes into_c return null instead of panicking.

unsafe-ffi ownership The same three moves as UniFFI, written by hand: a handshake (myotis_init, the twin of engine_init), a function that converts its arguments, calls host and hands back an owned string, and a free function. myotis_string_free takes the pointer back with CString::from_raw and drops it, like rustbuffer_free. Calling free(3) on the pointer would be undefined behavior. #[no_mangle] (edition 2021 spelling) here does what #[unsafe(no_mangle)] does in the macro output.

unsafe-ffi The header is the hand-written equivalent of UniFFI's metadata. It states the memory contract in prose, carries the payload history in comments, and defines MYOTIS_ABI_VERSION, which a capi.rs test and AbiVersionMirrorTest pin to the crate constant. (Lines 19–22 are out of date; see the callout below.)

  • unsafe-ffi The hand-written twin of FfiConverterString.lift. take copies the C string into a Kotlin String (toKString) and frees it in finally. For the arguments, cinterop maps a const char* parameter to Kotlin String? and converts the Kotlin string to a temporary C string for the duration of the call; the Rust side copies it (into_owned) before that memory goes away.
  • modules-cargo Static linking. staticLibraries = libmyotis_engine.a puts the Rust archive inside the cinterop klib, so the header and the library always travel together. EXPECTED_ABI_VERSION is the header's MYOTIS_ABI_VERSION macro, read by cinterop, and every public function calls requireAbi(), which compares it with myotis_init() once (by lazy is Kotlin's thread-safe lazy initialization).
