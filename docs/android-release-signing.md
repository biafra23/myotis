# Android release signing

Every release carries two Android APKs:

| asset | app | package | signed with |
|---|---|---|---|
| `Myotis-<tag>-android.apk` | **Myotis** (dark icon) | `com.jaeckel.ethp2p.android` | the Myotis **release key**, held only in GitHub Actions secrets |
| `Myotis-<tag>-android-debug.apk` | **Myotis Debug** (amber icon) | `com.jaeckel.ethp2p.android.debug` | the **debug key**, `android-app/debug.keystore`, which is public |

## Why two apps

Android accepts an update only from the signer of the installed app. The debug
keystore and its passwords are committed (`android-app/build.gradle.kts`), so
anyone can sign with it, and anything it signs can be "updated" by anyone. Until
this change the only Android asset was that debug build, under the release
package id. A lookalike APK could install over Myotis as an ordinary update, keep
its data, and answer the wallets with unverified data: exactly what Myotis exists
to prevent.

So the release app is signed with a key that never enters the repository, and the
debug build type is a separate app (`applicationIdSuffix = ".debug"`, its own
label and amber launcher icon, generated by `scripts/gen_android_icons.py` into
`android-app/src/debug/res`). The public key can then reach only the debug app.
Both apps install side by side. They default to the same JSON-RPC ports, so run
one at a time, or move one of them to other ports in Settings.

## How CI signs

`.github/workflows/android-apk.yml`:

1. **`build`** (every run) builds `assembleDebug` and `assembleRelease`. The
   release build type has no `signingConfig`, so it writes
   `android-app-release-unsigned.apk`. The Rust-engine and minSdk-29
   (`scripts/check_apk_min_api.py`) checks run on both APKs. On a tag the unsigned
   APK is uploaded as an artifact.
2. **`sign-release`** (v* tags only) is the only job that ever holds the key.
   - Its secrets live in the `android-release` **environment**, whose deployment
     rule admits v* tags only. A PR branch can't read them, whatever workflow it
     carries.
   - It checks out nothing but `scripts/sign_release_apk.sh` and
     `android-app/release-signing-cert.sha256`, and signs with the runner's
     `apksigner`. No Gradle, plugin or cargo build script runs while the key is
     on disk.
   - The script refuses an input that is already signed. After signing, it
     requires exactly one signer, equal to the pinned certificate (and the pin
     must not be the debug certificate).
3. **`release`** (v* tags only, `contents: write`, no key) checks the two package
   ids with `aapt2` and uploads both APKs.

It fails closed. Without the secrets, without a pinned certificate, or with a key
that doesn't match the pin, `sign-release` fails and `release` is skipped. That
tag then publishes **no** Android asset, rather than a debug-signed one under the
release name.

## One-time setup (owner)

1. **Generate the key on your own machine**, never in CI or a shared session.
   `keytool` prompts for the password:

   ```bash
   keytool -genkeypair -v -keystore myotis-release.p12 -storetype PKCS12 \
     -alias myotis-release -keyalg RSA -keysize 4096 -validity 10950 \
     -dname "CN=Myotis"
   ```

   **Back it up offline**, with its password, in at least two places. A lost key
   cannot be replaced: every installed copy would have to be uninstalled (losing
   its data) to move to a new key. A leaked key lets anyone ship "updates".
   Never commit it; `*.p12` / `*.jks` belong outside the checkout.

2. **Create the environment**, restricted to v* tags:

   ```bash
   gh api -X PUT repos/biafra23/myotis/environments/android-release \
     -F 'deployment_branch_policy[protected_branches]=false' \
     -F 'deployment_branch_policy[custom_branch_policies]=true'
   gh api -X POST repos/biafra23/myotis/environments/android-release/deployment-branch-policies \
     -f name='v*' -f type=tag
   ```

   Optionally, add yourself as a required reviewer (Settings → Environments →
   android-release). Every tag's signing step then waits for your click.

3. **Store the secrets in that environment**, not as repository secrets. `gh`
   prompts for each value, so a password never lands in your shell history:

   ```bash
   base64 -i myotis-release.p12 | gh secret set ANDROID_RELEASE_KEYSTORE_BASE64 --env android-release --repo biafra23/myotis
   gh secret set ANDROID_RELEASE_KEYSTORE_PASSWORD --env android-release --repo biafra23/myotis
   gh secret set ANDROID_RELEASE_KEY_ALIAS --env android-release --repo biafra23/myotis --body myotis-release
   ```

   `ANDROID_RELEASE_KEY_PASSWORD` is needed only for a JKS keystore whose key
   has its own password. PKCS12 has one password, and the script defaults to it.

4. **Pin the certificate.** Its SHA-256 is public. Commit it so every signing
   run checks the key against it:

   ```bash
   keytool -list -v -keystore myotis-release.p12 -alias myotis-release | grep 'SHA256:'
   ```

   Put the fingerprint into `android-app/release-signing-cert.sha256`, one line,
   colons allowed. Lines starting with `#` are comments. The release notes point
   users there to verify the download.

A tag push runs the workflow files from the tagged commit, so all of this must be
on the tagged commit (the pin) or in the repo settings (the rest) before the
first tag after this change.

## Verifying a download

```bash
apksigner verify --print-certs Myotis-<tag>-android.apk
```

The `Signer #1 certificate SHA-256 digest` must equal
`android-app/release-signing-cert.sha256`. On a phone, the AppVerifier app shows
the same fingerprint for an installed app.

## Migrating installs of the old debug-signed builds

Releases that shipped only an `*-android-debug.apk` installed the app as
`com.jaeckel.ethp2p.android`, signed with the public debug key. Android will not
update that install to the release-signed APK (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`,
shown as "App not installed … conflicts with an existing package"). The user must
uninstall it first.

That deletes its data: settings, allowed web origins, peer caches, sync state and
log-index subscriptions. `android:allowBackup="false"` means there is no restore.
Myotis holds no wallet keys or funds, so nothing is lost but re-sync time. The
release notes say this.

The package id stays `com.jaeckel.ethp2p.android` on purpose. Because the install
is refused, the old, publicly updatable app can't silently linger next to the new
one, as it would under a new id.

## Local builds

`./gradlew :android-app:installDebug` installs **Myotis Debug** (the `.debug`
package) next to a release install. `assembleRelease` gives the unsigned APK. To
sign it yourself, run the CI script with the same variables:

```bash
ANDROID_RELEASE_KEYSTORE_BASE64="$(base64 -i myotis-release.p12)" \
ANDROID_RELEASE_KEY_ALIAS=myotis-release \
ANDROID_RELEASE_KEYSTORE_PASSWORD=… \
  scripts/sign_release_apk.sh android-app/build/outputs/apk/release/android-app-release-unsigned.apk Myotis.apk
```

## Rotating the key

APK Signature Scheme v3 supports key rotation (`apksigner rotate`, then sign
with `--lineage`). Installs accept an update signed with the new key only through
that lineage, which needs the **old** key, another reason the backup in step 1
matters. Rotating means updating the secrets, the pin, and `sign_release_apk.sh`
(lineage flag) together.
